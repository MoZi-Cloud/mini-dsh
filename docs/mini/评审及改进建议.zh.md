# mini-DSH 方案与实现评审及改进建议 v1.1

[English](评审及改进建议.md) | 中文

## 摘要

当前源码已经形成可复用的 Project Ledger 内核：计划解析与导入、SQLite 相邻迁移、工作就绪计算、互斥租约和可重建 WorkPacket 均有明确实现。两个问题阻止它成为可信的自动执行闭环：验收 PASS 由模型调用直接声明，代码既不执行存储的 verifier，也不核对 `expected_exit_code` 等预期；计划激活没有正式写入操作，`plan/version-activated` 也没有载荷校验或回放状态。`dsh --profile mini` 只提供现有账本的读取和工作领取，无法从受支持入口导入并激活新计划。v1.6d 已按其收窄提案交付协作记录和认领可见性，不应误判为实现缺陷；是否继续增加认领授权、路径冲突阻断和完整多 Agent 调度，应在可信执行闭环和外部任务证据完成后单独决策。

## 1. 评审范围、版本与判定规则

本文是 `评审及改进建议` 的 v1.1 中文版，评审日期为 2026-09-21。精确源码版本由本文件的 Git 历史拥有，正文不固化提交哈希。评审对象包括 [v1.6 原始方案](HISTORY/fork-mini-DSH改造方案-v1.6.md)、[v1.6a 收敛方案](v1.6a/fork-mini-DSH改造方案-v1.6a.md)、[SQLite 核心账本附件](v1.6a/fork-mini-DSH-v1.6a-SQLite核心账本附件.md)、[v1.6b 完成报告](v1.6b/fork-mini-DSH-v1.6b-completion-report.zh.md)、[v1.6d 范围提案](v1.6d/fork-mini-DSH-v1.6d-collaboration-scope-proposal.zh.md)与[完成报告](v1.6d/fork-mini-DSH-v1.6d-completion-report.zh.md)、[real-use log](real-use-log.zh.md)，以及相关 package 和 benchmark 源码。

本文是参考型静态评审，不是完成报告。按任务边界，本轮不运行产品代码构建、源码类型检查或代码测试；完成报告中的测试数、覆盖率和持久账本结果属于报告证据，不是本轮独立复验结果。

### 1.1 证据等级

| 等级 | 证据 | 本文用法 |
| --- | --- | --- |
| A | 当前运行时代码、公开类型、数据库约束 | 判定当前强制行为 |
| B | 当前测试、README、Agent Note | 判断设计意图和已有覆盖；本轮未执行 |
| C | 完成报告、real-use log、历史方案 | 判断声称的结果、阶段目标和演进背景 |

当 A 与 B/C 冲突时，本文按 A 判定当前行为，并把冲突单独列为文档或验收问题。没有执行过的命令不写成“本轮通过”。

### 1.2 问题类别与优先级

| 类别 | 含义 |
| --- | --- |
| 实现偏差 | 当前源码违反已接受方案的明确安全、生命周期或产品入口要求 |
| 范围决策 | 当前实现符合已接受的收窄范围；进一步能力需要新的产品决策 |
| 证据缺口 | 代码或车道可证明一部分事实，但不足以支持更强结论 |
| 维护风险 | 当前行为可用，但重复所有权、过低抽象或文档漂移提高后续错误概率 |

P0 表示结果真实性、生命周期权威或受支持主流程存在缺口；P1 表示恢复性、可操作性或架构成本需要在继续扩展前处理；P2 表示证据与维护质量问题。优先级是本评审建议，不是源码已经声明的状态。

<a id="v10-review-corrections"></a>

## 2. 对 v1.0 评审的批判性修正

v1.0 找到了 verifier、activation、回放范围、协作记录和基准证据的核心差距，但混合了“当前实现错误”“提案有意不做”和“未来可选架构”。v1.1 作出以下修正。

| v1.0 判断 | v1.1 修正 | 修正依据 |
| --- | --- | --- |
| 把 report 多事务直接列为 P0 | 降为 P1 恢复性问题 | 每个底层写入自身原子；租约过期 reaper 会保留终态或把遗留的 IN_PROGRESS 重算为 READY/BLOCKED，当前证据不能证明永久损坏 |
| 把 v1.6d 未约束 claim 判为实现缺陷 | 改为范围决策 | [v1.6d 范围提案](v1.6d/fork-mini-DSH-v1.6d-collaboration-scope-proposal.zh.md) 明确要求 readiness 不变，阶段 A 只增加按 actor 的认领可见性，owner 写入也明确留在库函数 |
| 直接要求完整 durable receipt | 拆为最低修复与目标设计 | 最低要求是由受信执行者计算 verdict，拒绝模型自报 PASS；跨 session 审计是否需要独立 receipt 实体应由持久化需求决定 |
| 无条件冻结 schema v10 | 改为条件式进入标准 | 新迁移不是天然错误；只有新域绕开 P0 问题、继续扩大重复 parity 或没有真实消费者时才应拒绝 |
| 把版本化 plan 源文件列为确定缺陷 | 改为可选审计加固 | 当前数据库保存 source path/hash，Git 保存旧内容；只有脱离仓库历史仍需独立还原时，才必须增加内容寻址工件 |
| 使用提交哈希和多项易漂移计数 | 删除提交哈希，减少手写库存 | 文档规范要求精确版本由 Git 历史拥有，当前库存应由源码和完成报告查询 |
| 未检查受支持的首次使用路径 | 新增高优先级发现 | mini profile 的命令全部只读，配置只接收账本路径；基准通过库调用和直接 SQL 完成 import/activation |

v1.1 仍保留 v1.0 的两个最高优先级结论：自动验收结果不可信，计划生命周期不受正式写入和完整回放约束。

<a id="overall-conclusion"></a>

## 3. 总体结论

当前实现适合被描述为“实验性项目账本内核、工作领取工具和协作审计记录”。它已经支持在预先填充的账本上查询、领取、记录评价和读取审计结果，但尚未通过受支持入口建立账本，也不能证明自动 criterion 的 PASS 来自存储 verifier 的合规执行。

| 评审面 | 判断 | 类别 | 优先级 | 置信度 |
| --- | --- | --- | --- | --- |
| 计划解析、编译与事务导入 | 实现扎实，可继续复用 | — | 保留 | 高（A） |
| SQLite 版本和租约并发 | 关键不变式明确 | — | 保留 | 高（A） |
| 自动验收真实性 | 模型可直接声明 PASS，存储预期未被核对 | 实现偏差 | P0 | 高（A） |
| activation 与版本回放 | 无正式 activation writer，required event 无 decoder/fold | 实现偏差 | P0 | 高（A） |
| 受支持的首次使用路径 | profile 无 import/activate 操作 | 实现偏差 | P1 | 高（A） |
| report 中断恢复 | 可由租约过期恢复，但缺少一次尝试的幂等提交语义 | 维护风险 | P1 | 中高（A/B） |
| v1.6d 协作能力 | 符合收窄提案；不是认领授权系统 | 范围决策 | 决策项 | 高（A/C） |
| 4K 与 real-use | 能证明预算预检和集成路径，不能单独证明产品效果 | 证据缺口 | P2 | 高（A/C） |
| service 与 parity 组织 | 低层数据库句柄和重复比较扩大改动成本 | 维护风险 | P2 | 高（A） |

建议先修复两个 P0，再补受支持的 import/activate 路径。后续是否强化多 Agent 调度、增加新表或进入 v1.6c，应由外部任务效果和真实消费者决定。

<a id="implementations-to-retain"></a>

## 4. 应保留的实现

这些部分已经形成清晰的行为所有者。改进不应重写它们，只应在其公开操作上补齐缺失流程。

### 4.1 严格计划输入和事务导入

[YAML 解析](../../packages/experimental/project-ledger/src/parse-plan.ts)、[Schema 检查](../../packages/experimental/project-ledger/src/plan-schema.ts)、[语义检查](../../packages/experimental/project-ledger/src/plan-semantics.ts)与[计划编译](../../packages/experimental/project-ledger/src/plan-compile.ts)分层处理输入。[计划导入](../../packages/experimental/project-ledger/src/plan-import.ts) 在事务内写入不可变版本、工作项与对应事件。未知字段、错误引用和不支持的 schema 不依靠后续执行兜底。

### 4.2 SQLite 相邻迁移和失败关闭

[SQLite schema](../../packages/experimental/project-ledger-sqlite/src/schema.ts) 使用 STRICT 表、外键、部分唯一索引、单调 `user_version` 与相邻迁移注册表。新改进应追加迁移，不应改写已提交代次。

### 4.3 租约互斥和中断恢复

[租约实现](../../packages/experimental/project-ledger/src/lease.ts) 在 `BEGIN IMMEDIATE` 内重算 readiness、处理陈旧租约、追加事件并写入新租约，部分唯一索引提供最终仲裁。bearer token 只存哈希；进程遗失内存 token 后由到期和 reaper 恢复。reaper 对已进入 VERIFYING 或终态的工作项保留其状态，对遗留 IN_PROGRESS 重算 READY/BLOCKED，这也是 v1.1 不再把 report 多事务直接判为 P0 的原因。

### 4.4 可重建 WorkPacket

[WorkPacket 实现](../../packages/experimental/project-ledger/src/work-packet.ts) 保存确定性配方、引用与哈希，并支持重建和漂移检测。该机制比把整份 Master Plan 注入每轮上下文更符合项目目标，也为 verifier 绑定 packet、plan version 和代码基线提供现成标识。

### 4.5 插件扩展位置

[mini profile](../../packages/experimental/mini-profile/) 没有增加独立 Node 应用，也没有修改 agent loop。新增 activation、verifier consumer 和 owner 命令应继续位于 profile/plugin 组合中，不应增加 package bin 或第二套 workflow runtime。

<a id="main-findings"></a>

## 5. 主要发现与改进建议

本节把源码事实、与方案的关系、风险和建议分开。每项建议先给出满足既有方案的最低修复，再给出需要额外持久化或产品决策的目标方案。

### 5.1 F-01 / P0：自动验收结果由不受信输入决定

#### 源码事实

[evaluateAcceptanceCriterion](../../packages/experimental/project-ledger/src/acceptance.ts) 把结果定义为 caller-reported，并直接把 `PASS` 映射为 PASSING。`verification_ref` 可以为空，函数不读取对应 `verification_specs` 来核对 verifier kind、命令、查询、预期退出码或预期 JSON。

[project_work_update report](../../packages/experimental/mini-profile/src/project-work.ts) 允许模型提交 `{criterionId, result, exitCode?, outputTail?}`。`result` 决定 criterion 状态；`exitCode` 和 `outputTail` 只是可选观察数据。调用者可提交 `PASS` 而不提供退出码，也可同时提交 `PASS` 和失败退出码，当前代码不会比较 `expected_exit_code`。

`isAgentObservable` 只检查 verifier 是否有 `command_text` 或 `query_text`，不执行 COMMAND/TEST，也不解释 SQL_ASSERTION/GRAPH_ASSERTION 的预期。`sandbox_required` 和 `approval_required` 会进入存储和 WorkPacket，但 report 路径不检查它们。

[real-use worker](../../benchmarks/real-use/run-real-use.worker.ts) 通过 `spawn('sh', ['-c', command])` 执行命令，再把结果报告给正式工具。该车道证明工具可以记录外部结果，但它绕过 `ctx.shell` 的结构化 sandbox 结果和运行时 `ctx.approval`；它也无法使产品工具拒绝伪造 PASS。

#### 与方案的关系

[v1.6a §18](v1.6a/fork-mini-DSH改造方案-v1.6a.md#18-verifier-信任边界) 要求 COMMAND/TEST 经现有 shell、sandbox 和 approval 执行，禁止 Project Ledger 直接运行命令或绕开策略。当前 ledger package 确实没有执行命令，但 consumer 也没有提供受信执行链，因此“ledger 不执行”和“系统可信验证”之间仍有缺口。

需要区分两个 approval：v1.6b 的 ledger `approvals` 是项目决策记录；运行时 `ctx.approval` 是一次工具执行的用户授权。`verification_specs.approval_required` 应映射后者，不能用一条项目 approval 行替代运行时许可。

#### 最低修复

1. 把现有写入语义命名为 reported evaluation；模型自报结果不能使 COMMAND、TEST、SQL_ASSERTION 或 GRAPH_ASSERTION 自动 PASSING。
2. 在 mini profile 增加受信 verifier consumer。该 consumer 从 ledger 读取 spec，自行计算 verdict，不接受模型传入 `result`。
3. COMMAND/TEST 通过 `ctx.shell.resolve()` 和 `ctx.shell.run()` 执行，并核对退出码、超时、abort、sandbox denial 和 runner failure。`sandbox_required` 为真时，缺少 sandbox 执行事实必须失败关闭。
4. `approval_required` 为真时，从持有 Agent 的开放 turn 调用运行时 `ctx.approval`；approval service 要求 turn 内审计，consumer 不能在无 session 的后台脚本中伪造许可。
5. SQL_ASSERTION/GRAPH_ASSERTION 在没有受信解释器前保持不可自动完成；OWNER_CONFIRMATION 只接受 owner 操作。

#### 目标方案

若验收证据需要跨 session 独立审计，增加稳定的 verification run/reference，绑定 criterion、spec 内容哈希、plan version、WorkPacket 或 repo baseline、执行策略和结构化结果。若当前事件与 evaluation 已能完整保存这些事实，可以复用现有表和事件，不必为了“receipt”名称增加新实体。

### 5.2 F-02 / P0：计划激活缺少权威写入，required event 不验证也不回放

#### 源码事实

[计划导入](../../packages/experimental/project-ledger/src/plan-import.ts) 正确创建 DRAFT 版本，但当前没有 `activatePlanVersion`。[context-light worker](../../benchmarks/context-light/run-4k.worker.ts)、[real-use worker](../../benchmarks/real-use/run-real-use.worker.ts) 和测试通过直接 SQL 把版本改为 ACTIVE；real-use 的更新没有写入 `activated_at_ms`。

[PROJECT_EVENT_TYPES](../../packages/experimental/project-ledger/src/project-events.ts) 把 `plan/version-activated` 列为 required event，但 replay switch 没有该 case，也没有对应 payload decoder。该事件落入 default，不校验 `activatedBy` 或目标版本；当前测试专门把它作为“词表内但无 projection effect”的事件使用。

`ReplayedPlanVersion` 不包含 status、激活/接替时间和当前版本指针。[project replay](../../packages/experimental/project-ledger/src/project-replay.ts) 与 [doctor](../../packages/experimental/project-ledger/src/doctor.ts) 因而无法发现这些生命周期列被直接改写。supersede 有正式 writer，但回放仍不重建完整版本生命周期。

#### 与方案的关系

[v1.6a §8](v1.6a/fork-mini-DSH改造方案-v1.6a.md#8-plan-导入不是激活) 要求 activation 是 owner explicit action；BOOT-04 要求事件回放等于 current projection。方案的 W00–W12 工作分解没有为 activation writer 单列工作包，这一遗漏使方案要求和实施清单本身不闭合，不能只归因于实现者漏写函数。

#### 最低修复

1. 定义 owner-authorized activation operation，在一个事务中校验 DRAFT、现役版本约束和导入诊断，更新 status、`activated_at_ms`、`plans.current_version_id` 并追加严格的 `plan/version-activated`。
2. 为 activation event 增加 payload decoder。required event 即使暂时不改变 fold，也必须验证引用和载荷；推荐直接把版本 status 与当前指针纳入 fold。
3. 让 supersede 与 activation 的组合语义只有一个所有者。若切换要求两者同时成功，应提供原子 switch operation；若允许中间没有 ACTIVE 版本，文档和调用者必须明确该状态。
4. 基准和测试 fixture 通过正式 operation 建立 ACTIVE 状态，不再直接更新生命周期列。

#### 目标方案

回放投影包含版本 status、激活时间、接替时间和每个 plan 的 current version。任一直接 SQL 篡改都由 replay audit 报告。若团队决定生命周期列不属于事件重建范围，则必须收窄 BOOT-04 和完成报告的表述，并保留独立数据库约束与 doctor 检查；不能继续声称完整 current projection 可回放。

### 5.3 F-03 / P1：受支持的 mini profile 无法建立首个可工作账本

#### 源码事实

[MiniProjectLedger](../../packages/experimental/mini-profile/src/index.ts) 的配置只有 ledger path 与 busy timeout；服务只负责打开数据库。[`/project` commands](../../packages/experimental/mini-profile/src/commands.ts) 明确只读，没有 import、activate 或 supersede 命令。`project_work_*` tools 假定数据库已经包含 ACTIVE plan 和可领取工作项。

基准可通过 `importPlanVersion`、`supersedePlanVersion` 和直接 SQL 建立状态，因为它们是仓库内 worker。普通用户从受支持的 `dsh --profile mini` 入口无法完成“plan.yaml → import DRAFT → owner review → activate → claim”。

#### 与方案的关系

[v1.6a §4](v1.6a/fork-mini-DSH改造方案-v1.6a.md#4-应用入口禁止独立-mini-dsh-node-bin) 把 `dsh --profile mini` 定义为唯一产品入口，并把 `/project import` 列为优先的人类交互面。当前库能力存在，产品入口没有承接它。

#### 改进建议

增加 owner-only `/project import <plan-path>`、`/project activate <version>` 和必要的 `/project supersede` 操作，或提供等价的 GUI owner flow。import 必须只解析、验证和写入 DRAFT，不能执行 verifier；activate 必须展示诊断、baseline 和目标版本，并经明确 owner action。所有入口调用 F-02 的同一 service operation，不复制 SQL，不增加 package bin。

### 5.4 F-04 / P1：report 缺少一次尝试的幂等提交语义

#### 源码事实

`project_work_update report` 先 heartbeat，再逐条提交 evaluation，再分别移动 VERIFYING/DONE/FAILED，最后释放租约。每一步自身原子，但一次 report 不是一个事务，也没有 operation id。

进程中断可能留下部分 evaluations 和活跃租约。现有 lease reaper 能在到期后恢复：终态保持不变，IN_PROGRESS 重算为 READY/BLOCKED。因此该情况不是已证实的永久损坏，也不应继续列为 P0；代价是恢复延迟、重复 evaluation 和“本次尝试完成到哪一步”的不确定性。

#### 改进建议

先定义期望语义，再选择机制：

1. 如果一组 criterion verdict 和状态移动必须同时可见，在 verifier 已于事务外完成后，用一个 ledger operation 在单个 `BEGIN IMMEDIATE` 中提交全部 evaluation、工作状态和租约结束。
2. 如果需要保留逐步提交，增加 attempt/operation id 和明确阶段，使重试能够识别已写步骤并幂等完成或终止。
3. 对每个写点做故障注入和进程重启测试，验证立即重试、等待 reaper 和重复 report 的结果；不能只验证各底层函数的独立回滚。

### 5.5 F-05 / P2：ProjectLedger service 的抽象层级过低

[MiniProjectLedger](../../packages/experimental/mini-profile/src/index.ts) 公开 `db: DatabaseSync`，commands 和 work tools 直接执行 SQL 或调用接收 `DatabaseSync` 的库函数。这不是当前行为错误，也不必为了理论上的 provider 可替换性立即重写；但它使 activation、受信 verification 和原子 report 无法由一个稳定 service operation 拥有，consumer 也容易重新组合出不同事务语义。

建议先把 F-01 至 F-04 需要的操作定义为 `ProjectLedger` service methods，再让 SQLite provider 实现。迁移应按消费者需求进行，优先覆盖 import/activate/switch、claim、verify/report、todo 和 replay；没有第二个消费者或事务所有权需求的只读函数可以暂时保留为库 API。

### 5.6 F-06 / 决策项：v1.6d 已交付记录能力，是否加入调度约束尚未决定

#### 当前范围

[v1.6d 范围提案](v1.6d/fork-mini-DSH-v1.6d-collaboration-scope-proposal.zh.md) 明确保留原 readiness 和 todo 计算，只增加工作指派、交接、范围预留、冲突记录和按 actor 的认领可见性。当前 [claimWorkItem](../../packages/experimental/project-ledger/src/lease.ts) 不读取 assignment、handoff、reservation 或 conflict，符合该收窄范围。

scope reservation 只对 `(project_id, scope_kind, scope_value)` 完全相等值排他；父子路径重叠由 conflict 记录而不是 reservation 阻止。完成报告已经公开这一限制，因此它是已知语义，不是隐藏实现错误。

#### 后续决策

如果产品只需要协作审计和认领可见性，保持现状并修正文档名称即可，不应增加调度复杂度。如果真实使用要求系统阻止未授权领取或路径重叠，再分别决策：

- session agent 与 ledger actor 的稳定映射；
- 哪些 assignment kind 授权 claim；
- handoff 是记录还是转移 claim 权；
- PATH reservation 是否做规范化及祖先/子孙重叠；
- open conflict 是否进入 readiness blocker。

这些规则必须由两个独立 Agent session 的失败案例驱动，不能仅因表已经存在就全部启用。

### 5.7 F-07 / P2：验证车道证明的事实弱于阶段进入结论

[context-light README](../../benchmarks/context-light/README.zh.md) 已诚实区分 deterministic 和 live lane。源码中的 deterministic lane 使用私有 `project_work_*` fixture、脚本 adapter 和 `ceil(bytes / 4) + 512` 预检；只有显式 live lane 使用 provider-reported usage。因此 keyless 结果能证明固定序列、请求装配和估算预算，不能证明 shipped mini-profile tools 或真实模型完成任务。

[real-use README](../../benchmarks/real-use/README.zh.md) 也明确说明没有模型。该 lane 使用 shipped work tools，适合证明持久账本、claim/report 和读审计集成；直接子进程 verifier 与固定 lane identity 不足以证明模型判断质量、运行时权限或多 Agent 并发。

建议保留车道并收紧结论：

| 车道 | 可作为进入依据的事实 | 不能单独支持的结论 |
| --- | --- | --- |
| deterministic 4K | 固定请求在启发式预算内；计划全文未注入 | 真实 tokenizer、模型任务成功、正式工具一致性 |
| live 4K | 固定 provider 的 reported input usage 与实际模型交互 | 普遍模型效果或多任务稳定性 |
| shipped-profile integration | 正式 tools、SQLite 和状态迁移贯通 | 模型自主性、sandbox/approval 合规 |
| external-task effectiveness | 非 ledger 任务相对基线的成功率、token、重试 | 多 Agent 并发，除非使用独立 session |
| multi-agent concurrency | 独立 session 的竞争、交接和恢复 | 单进程依次写入两个 identity 不构成此证据 |

阶段进入门应至少包含若干非 Project Ledger 自举任务，并与“不使用 ledger”的基线比较。golden 实现任务继续作为回归数据，但不应单独承担产品价值确认。

### 5.8 F-08 / P2：重复 parity 和 current-state 文档漂移提高扩展成本

[doctor](../../packages/experimental/project-ledger/src/doctor.ts) 与 [project replay](../../packages/experimental/project-ledger/src/project-replay.ts) 分别维护跨实体族的投影比较；[project-events.ts](../../packages/experimental/project-ledger/src/project-events.ts) 同时拥有大部分事件类型、decoder 和 fold。新领域必须同步多处字段比较，activation 已展示“词表已登记但 decoder/fold 缺失”可以穿过现有组织。

建议由 `readProjectReplay` 拥有唯一 projection parity，doctor 只转换 drift 并增加 replay 无法表达的运行健康检查。事件 decoder/applier 按领域拆分后由显式注册表汇总；required 类型必须在注册时同时提供 decoder 和 fold policy，不能依赖 switch default。

当前 package README 也有明显漂移：[project-ledger README](../../packages/experimental/project-ledger/README.zh.md) 的限制仍写 “No activation or supersede yet”，但 supersede 已存在；[SQLite README](../../packages/experimental/project-ledger-sqlite/README.zh.md) 的迁移说明停在较早代次；package descriptions 仍以 v1.6a 和初始表数描述当前包。完成报告可以冻结历史，README 和 manifest description 应只描述当前行为并链接历史报告。

版本化 plan 源文档属于可选加固：如果审计必须脱离 Git 历史独立还原旧输入，再增加版本命名文件或内容寻址 artifact；否则 source hash、path 与仓库历史可以继续作为既定证据组合。

<a id="phased-proposal"></a>

## 6. 分阶段实施建议

实施顺序以关闭错误状态为先，不以新增表数或版本号为目标。

### 阶段 A：恢复结果真实性和版本权威

- 实现 F-01 的受信 verifier consumer，使 executable criterion 的 verdict 由代码根据存储 spec 计算。
- 实现 F-02 的 activation/switch operation、严格 activation event decoder 和版本生命周期回放。
- 把当前 caller-reported 数据明确标记为 reported，不再让它自动代表 verified。
- 将 benchmark 的直接 SQL activation 和直接 verifier spawn 迁移到正式操作；在完成前，报告继续明确这些限制。

退出条件：伪造 PASS 不能使工作 DONE；所有 ACTIVE 版本都可追溯到合法 activation event；生命周期直接篡改可被审计发现。

### 阶段 B：完成受支持入口和中断语义

- 在 `dsh --profile mini` 增加 owner import/activate/supersede 流程。
- 为 report 选择原子提交或带 operation id 的可恢复提交，并覆盖写点故障。
- 让新增操作通过 typed ProjectLedger service 拥有事务，不再由命令、工具和 benchmark 分别组合 SQL。

退出条件：新用户只通过受支持 profile 即可从 plan 文件建立可领取项目；report 在任一写点中断后有确定、可测试的恢复结果。

### 阶段 C：收敛重复实现和验证证据

- 合并 replay/doctor 的 projection parity 所有权，拆分事件 decoder/applier 组织。
- 让 deterministic 4K 使用 shipped tools，继续把启发式预算与 provider usage 分开报告。
- 用非 ledger 仓库任务建立 live-model 对照结果，记录成功率、token、重试和人工介入。
- 修正 README 与 package description 的 current-state 漂移。

退出条件：新增事件不能只登记类型而遗漏 decoder/fold policy；产品价值结论不依赖自举任务或 keyless 脚本 Agent。

### 阶段 D：决定是否强化多 Agent 调度或进入 v1.6c

- 先观察独立 Agent session 中实际发生的授权、交接和范围冲突问题。
- 只实现被案例要求的 assignment、handoff、reservation 或 conflict 强制规则。
- v1.6c 继续服从 signature/call-site extractor 研究门；declared intent 不升级为自动阻断事实。

退出条件：每条新调度规则有现实失败案例、唯一行为所有者和无规则时的对照证据。

## 7. 建议验收矩阵

以下标准用于下一轮实现评审，不表示本轮已经执行。

| 编号 | 对应发现 | 验收条件 |
| --- | --- | --- |
| A-01 | F-01 | 模型只提交 `result: PASS` 且没有受信执行结果时，criterion 不进入 PASSING，工作项不能 DONE |
| A-02 | F-01 | COMMAND/TEST 的实际退出码与 `expected_exit_code` 不同，即使调用参数声明 PASS 也记录失败 |
| A-03 | F-01 | `sandbox_required` 为真而执行结果无 sandbox facts、runner failed 或发生 denial 时，验证失败关闭 |

| A-06 | F-02 | activation 在一个事务内写 status、时间戳、current pointer 和 required event；任一写入失败全部回滚 |

| A-09 | F-03 | 空账本可从 `dsh --profile mini` 通过 owner import 与 activate 建立第一个 READY work item，无外部脚本或直接 SQL |
| A-10 | F-04 | report 每个内部写点的故障注入均得到规定状态；同一 operation 重试不重复产生逻辑结果 |

| A-14 | F-06 | 只有在决定启用路径互斥后，PATH reservation 才必须拒绝相等、祖先和子孙重叠；保持 advisory 时文档必须明确 |

<a id="final-assessment"></a>

## 8. 最终判断

v1.6a 的核心数据结构和租约设计不需要推翻，v1.6b 与 v1.6d 已记录的数据也不需要回滚。项目应先修复两处会改变事实含义的问题：系统当前无法证明 PASS，事件当前无法证明哪个计划版本被合法激活。随后补齐 `dsh --profile mini` 的 owner 写入路径，使方案描述的纵向切片第一次成为普通用户可走通的受支持流程。

report 原子性、typed service 和 parity 拆分属于紧随其后的恢复性与维护工作，不应与 P0 混为一谈。v1.6d 当前实现符合其收窄范围，最准确的名称是“协作记录与认领可见性”；只有真实并发使用要求系统做授权或冲突阻断时，才把这些记录升级为调度规则。

在上述退出条件满足前，不建议用更多表、事件类型或自举工作项作为阶段完成依据。进入新领域的证据应来自受支持产品路径、真实执行权限、非 ledger 任务和可复现对照结果。
