# 0. 总体结论

一句话判定：**方向成立、建模成熟度高于多数同类方案，但当前版本不可实施——存在一个阻断级缺陷（前置体系不在仓库）和两处与仓库硬规则的冲突；且规模与 "mini" 初衷倒置，缺分级交付路径。**

六条核心判定：

1. Plan-as-Data 的中心主张（计划即数据、worker 只领取有界工作包、不重读数千行 Markdown）成立，且与 DSH SessionEvent 的 append-only / projection 工程思想同构，值得做。
2. **阻断级**：v1.4/v1.5 前置体系（SQLite 项目记忆库、symbol/call graph、TypeChecker 提取器、4K 基准、v1.5 迁移 fixture）在本仓库内完全不存在。附件自称 "只描述 v1.6 delta"，导致方案在仓库内既不可评审也不可实施。
3. 以 mini-swe-agent（190 行 agent 核心，SWE-bench Verified >74%）和本仓库现成的 sdk-minimal bundle（158 行 cordis.patch.yml）为参照：v1.6 一次规划了 51 张新表、31 个规定签名的函数、13 个阶段，是 "mega" 级投入，没有降级路径。
4. Function Contract 域把 effects / PROHIBIT 调用边当作可机械提取、可判定的事实，超出 TypeScript 静态分析能提供的保证；应降级为签名级硬门 + 声明性意图记录。
5. 与仓库既有体系的三处集成点未定义：应用启动规则（`mini-dsh` CLI 直接冲突）、既有 plan-mode / tool-todo 两层会话级计划体系、workflow 引擎双模型。
6. 配套 JSON Schema 与方案自身的 fail-closed 主张矛盾（`additionalProperties: true` 泛滥、关键枚举缺失），"机器可校验" 目前不成立。

# 2. 值得肯定的设计

1. **自举验收（BOOT-01..08）是全案最强的部分。** 用自身 plan 做 golden fixture、强制 "v1.6 自己必须能被机器导入"，比任何演示都有说服力，也直接检验了 §0 的主张。

5. **复用而非重建执行层**：§47 明确 workflow/subagent 执行复用 DSH 能力；§78.20 明确不重写 agent loop，与仓库 "Plugins, not loop changes" 规则一致。
6. **测试纪律成熟**：每个 WP Red→Green、并发 claim 测试、事件回放对账、10 万工作项 / 百万事件 synthetic、query-plan 门。
7. **产品判断清醒**：§57 拒绝虚假百分比、要求结构化状态输出；§1 对 v1.5 局限的自我批判准确诚实。

# 3. P0 阻断级问题（不解决则无法开工）

## P0-1 前置体系不在仓库，附件不可独立实施

附件开篇声明 "基础：v1.4 + v1.5 schema 全部继续保留"，但：

- v1.5 的 SQLite 记忆库（repositories / symbols / symbol_versions / call_sites / analysis_units）、content store（全部 `*_content_id` 字段的宿主）、TypeChecker 图，仓库内无任何定义；
- WP01 要求 "v1.5 DB fixture → v1.6" 迁移，fixture 不存在，Red 阶段无从写起；
- DoD 第 27 条 "4K Context-Light benchmark 不回归"：benchmarks/ 内无对应物，该条当前既不能通过也不能失败；
- BOOT-02 依赖 `mini-dsh project next`，而该命令的实现载体（见 P0-2）也不存在。

**建议**：将 v1.4/v1.5 的方案文档与 schema fixture 一并入库（docs/mini/ 或独立 fixtures 目录），或在 v1.6 开头显式列出前置物清单与存放地；4K lane 先给出可执行定义（建议：工作包含系统提示片段的总 token 预算 4,096）并落地基准脚本，再进入 DoD。

## P0-2 `mini-dsh` CLI 与仓库应用启动规则直接冲突

AGENTS.md：**只有 `dsh` profiles 可以启动 Node 应用；package bins、demos、公共 SDK argv 逃逸均被禁止**（verify-application-entrypoints 脚本强制）。提案通篇使用 `mini-dsh plan import`、`mini-dsh project todo --owner`、`mini-dsh project next --agent` 作为入口。

**建议**：二选一并写入方案——(a) 定义为某个 `dsh --profile`（如 profile `mini`）下的子命令面，复用 packages/boot/cmdline 既有机制；(b) 作为 headless profile 的任务类型。同时按仓库规则更新 docs/architecture.md 的扩展点表。若维持独立 bin，会在 CI 门上直接红灯。

## P0-3 配套 Schema 与 fail-closed 主张自相矛盾

§6 要求 "plan doctor 缺任何硬必需项都必须 fail closed"，但 `mini-dsh-plan-v1.schema.json`：

- 除根对象外几乎全部 `additionalProperties: true`，未知字段畅通无阻，与 §23 "unknown field 保留或拒绝按 policy" 的最松选项绑定；
- `workItem.type` 无枚举（方案 §7 明确了 13 种 work_type）；`phase.status` / `workItem.status` / `acceptance.kind` 全为自由字符串；同一文件内 `plan.status` 却有枚举，宽严不一；
- `verifier` 仅 `{"type": "object"}`，command / test / benchmark / owner 四种验证器无判别结构，`expected` / `target` / `role` 等语义字段全靠约定；
- §6 的 24 项最低能力中，actors / assignments / 独立 hierarchy 表达 / phase gates 等，schema 均未覆盖；`targets.verifyBy`、`decisions.blockingLevel` 等文档语义靠 additionalProperties 吸收。

对照仓库规则 "Misconfiguration fails loud"。**建议**：v1 即收紧——各层 `additionalProperties: false`、全部受控词表枚举、verifier 做判别联合（kind → required fields），未知字段策略选 "拒绝" 并与 schemaVersion 升级路径配套。schema 是这个体系的宪法，第一版松了以后收不回来。

# 4. P1 高风险问题

## P1-1 规模倒置：先建管理系统，后证产品价值

mini-swe-agent 的 AGENTS.md 写着 "write the simplest, smallest, most readable agent / This repository rewards minimal code"，其 190 行核心拿到 SWE-bench Verified >74%；本仓库现成的最小组合 sdk-minimal bundle 只有 158 行。v1.6 在写第一行业务代码之前，先规划了 51 张表、31 个函数、13 个阶段——这是把 GitLab Work Items + Redmine Journal + OpenProject baseline 的业务模型整体搬进一个个人 fork。

v1.6 承诺的核心价值（§0：worker 不重读 Markdown，只领有界工作包）实际只需要：plan.yaml → 校验 → 事务导入 → work packet 查询。

**建议切为四级，每级有独立价值与回退点，级间用上一级的真实使用证据门控：**

```text
v1.6a Ledger 核心   plans/plan_versions/work_items(+relations)/acceptance/project_events
                    + doctor + import + project next/todo + buildWorkPacket（约 10 张表）
                    → 直接满足 §0 主张与 BOOT-01/02/03/08
v1.6b Owner 域      decisions/approvals/resources(+requirement/instance/verification)
v1.6c Contract 域   design_objects/change_specs/contracts/…（research-gated，见 P1-2）
v1.6d Multi-agent 域 actors/assignments/leases/handoff/scope/workflow 镜像
```

lease 表很便宜（一张表 + 一个 partial unique index），可以从 v1.6d 提前到 v1.6a 末尾，让 BOOT-06 尽早落地。

## P1-2 Function Contract 的可判定性被高估

这是全案技术风险最高的域：

- **effects（REQUIRED/ALLOWED/PROHIBITED）无法从 TypeScript 源码机械提取**。TS 没有 effect system；§27 声称 baseline contract "结果必须可由 pinned source 重建"，对 effects 不成立，只能靠人工标注或注释约定；
- **PROHIBIT 调用边需要含动态分发的全程序调用图**。仓库现有 typert 是构建期"类型 → Zod 工厂"，没有 call-site 提取器（全库 grep 无 callSites/call_graph 命中）；v1.5 语境里的提取器又不在仓库（P0-1）；
- **`return_type_text` 等以文本存储再比较**：格式化差异、导入别名、泛型展开都会产生假阴性；
- `compareFunctionContracts` 比较参数"semantic role"之类字段，这些字段的来源方案未定义。

**建议**：分层降级——签名级（TS 类型结构比较，tsc 或类型图）+ required RETAIN 调用边（提取器存在后才启用）做硬门；effects 与 PROHIBIT 边降级为 declared-intent：先记录、后验证，验证缺失不得阻塞 DONE。BOOT-05（错误返回类型必须 FAIL）保留，签名比较即可支撑。§15 的四态（OBSERVED_BASELINE/TARGET/IMPLEMENTED/VERIFIED）对签名成立，对 effects 只对前两态成立，方案应如实标注。

## P1-3 与既有 plan-mode / tool-todo 的关系未定义

仓库已有两层会话级计划体系：`dsh-plan-mode`（/plan 进入、用户审阅后执行、跨 resume/fork 存活）与 `dsh-tool-todo`（todo_write 整表替换、session log 投影、UI 呈现）。v1.6 引入第三层 project work_items，三层的边界与桥接只字未提：会话 todo 是否投影自 work_items？plan-mode 产出的计划能否导出为 plan.yaml？agent 在会话内完成的任务如何回写 work item 状态？

**建议**：增加 "与既有计划/任务体系的关系" 一节，按仓库 capability-seam 规则补齐 Service Definition / Provider / Consumer 三角色；否则会出现三个互不感知的 todo 来源，正是方案自己批评的 "混成一张万能表" 的翻版。

## P1-4 SQLite 作为 source of truth 的版本与运行时策略缺失

上游两个先例采取了相反策略：storage-sqlite 版本不符即**拒绝**（数据是事实源）；session-query-sqlite 版本不符即**重置**（数据是可重建的派生索引）。project DB 明确是事实源，必须选 "拒绝 + 相邻迁移" 策略，并落实仓库规则 "SQLite uses monotonic SCHEMA_VERSION"（PRAGMA user_version）。附件对以下运行时事实完全未提：journal mode（WAL？）、busy_timeout、单写者假设下的 BUSY 重试、`project_events.sequence_no` 的分配方式（并发下 MAX+1 必须在 IMMEDIATE 事务内才有意义）。

**建议**：附件增加 "运行时约定" 一节，逐项写死；迁移策略对齐 session-format 的相邻迁移包模式，禁止原地改表。

## P1-5 project_events 的事件模式演进策略缺失

上游为 SessionEventMap 建了完整机制：单调 SESSION_FORMAT_VERSION、未知事件 required-on-read 默认拒绝、可忽略事件带 `ignorable: true` 信封。project_events 的 event_type 词表和 payload 必然演进，方案没有任何对应策略——第一版上线后，第二版新增事件就会破坏 replay 与 projection 对账，恰好击穿 §64 的 WP04 验收。

**建议**：直接移植 SESSION_FORMAT_VERSION 机制（事件信封版本 + ignorable 语义），不要新发明。

## P1-6 workflow 双模型的权威性未定

附件 #30-31 在 DB 里建了 workflow_definitions/nodes/edges/runs 全套图模型；§47 又说 "实际执行可继续复用 DSH workflow/subagent 能力"。packages/workflow 已有自己的定义与运行模型，两份 definition + 两份 run 状态的同步策略未定义。

**建议**：DB 只做投影——definition 由 plan 导入后交给引擎，run 状态由引擎事件回写（复用 P1-5 的事件机制）；或明确 DB 为 definition 唯一权威、引擎无持久定义。二选一，写明。

## P1-7 WorkPacket 与 "Model-visible ⟺ logged" 不变量的关系

`buildWorkPacket` 的产物会进入 worker 的模型请求。仓库硬规则：凡到达模型请求的内容必须可从 session log 重建。方案未定义 packet 是全文入 session event，还是只记录 "DB 引用集 + 确定性构建器"。

**建议**：选后者（省 token，符合 Context-Light 初衷），但要求构建器版本随引用集入 log；在 §37 补一段明确此契约，并在 runtime invariants 里加对应断言。

# 5. P2 中等问题

1. **golden fixture 内嵌 Android 物理设备任务**：`OWNER-ANDROID-001`（Android 11+ 真机）在 CI 与多数本地环境不可满足，P05 里程碑将永久 blocked，bootstrap plan 的项目状态永远 "不干净"，§57 的结构化状态会常年挂着 Environment-blocked。资源验证的三分模型是好设计，但示例应放测试 fixture；bootstrap plan 内改用普遍可满足的资源（如 DEEPSEEK_API_KEY 的 provision/verify 流程，正好复用仓库 credentials 域语义）。
2. **plan.yaml 无 actors/assignments**：§6 最低能力第 14/15 项未被 golden fixture 覆盖；BOOT-06 需要 agent-1/agent-2 两个 actor，而导入器不创建 actor，其来源（首启种子？agent 注册时自建？）未定义。建议方案明确首启种子规则（系统创建 Owner + Coordinator；agent 首次 claim 时自建 actor），并让 fixture 覆盖。
3. **`work_items.plan_version_id NOT NULL`** 排斥计划外工作（agent 途中发现的突发 bug 无家可归），与 §7 "统一工作底座" 主张冲突。建议允许 NULL 或引入默认 backlog plan。
4. **`plans.status` 与 `plan_versions.status` 双状态字段**：权威归属未定义，必然漂移。建议 plans 去掉 status，由 current_version_id 派生。
5. **lease 生命周期未闭合**：过期回收者（reaper）、心跳节奏、持有者崩溃后 attempt 与新 lease 的衔接未指定。partial unique index + BEGIN IMMEDIATE 的组合是对的，回收是语义缺口。动手前按仓库要求读 docs/defensive-patterns.md。
6. **verifier command 的信任边界**：plan.yaml 可携带任意命令，"导入 + 激活" 即构成执行面。建议：activation 强制 OWNER actor 执行；verifier 命令一律经 dsh-shell seam 走既有 sandbox/approval 策略；schema 层限定 verifier kind 词表。
7. **baseline 漂移**：fork 跟踪 upstream，mid-plan merge 会让 pinned baseline 过期；§35.10 有 "baseline/target contract still valid" 检查项但没有对应流程（在途 attempt 作废？重新捕获 baseline？supersede 计划？）。
8. **双编号体系**：WP00–WP16（17 项）与 P00–P12（13 阶段）粒度不一致且无映射表，执行对账必然混乱。建议 plan.yaml 的 phase title 内标注对应 WP 区间，或直接统一为一套。
9. **FK 覆盖不一致**：work_items 有 project FK 却无 plan_versions/phases/milestones FK；work_external_blockers、handoffs、milestones 等多表零 FK。STRICT 表应统一补齐并声明 PRAGMA foreign_keys=ON。
10. **supersede 对在途状态的处置未定义**：旧 plan version 上的活跃 lease、未完结 attempt、历史 evaluation 是整体迁移、冻结还是照常收尾，方案未答。

# 7. 建议的 v1.6a 垂直切片（最小可交付）

```text
表（10 张）：plans, plan_versions, phases, work_items, work_item_relations,
            work_external_blockers, acceptance_criteria, verification_specs,
            acceptance_evaluations, project_events
            （+ plan_imports / plan_compile_diagnostics 作为导入审计，共 12 张）
函数（8 个）：parsePlanDocument, validatePlanSchema, compilePlan(裁剪版),
            importPlanVersion, planDoctor, computeProjectStatus,
            project next / project todo, buildWorkPacket
验收：BOOT-01（导入+doctor 零错误）、BOOT-02（fresh agent 只靠 DB 取任务）、
      BOOT-03（owner/agent todo 分离）、BOOT-08（版本升级历史）
再加 work_leases（1 张表 + 1 个 partial unique index）即可覆盖 BOOT-06。
```

这一级独立成立：即使后续三级全部不做，"计划可查询、任务可领取、状态可结构化" 的价值已经交付，且全程不触碰 agent loop。v1.6c（Contract 域）建议加显式研究门：先在侧分支证明 call-site 提取器与类型结构比较的可行性，再立 WP。

# 9. 结论

这份方案的作者对 DSH 的不变量体系（append-only、projection、fail-closed、版本化迁移、复用 seam）内化程度很高，§18 的源码级示例经实测逐项吻合，建模分离的多处决策正确。它的真正问题不在对错，而在**次序与范围**：在一个前置体系尚未入库、命令载体与仓库规则冲突、schema 尚未收紧的起点上，一次性规划了 51 张表与 13 个阶段。

建议的处理顺序：先清 P0（前置入库、CLI 形态定案、schema 收紧——三者都是文档级工作，一两天内可完成），然后按第 7 节的 v1.6a 切片落地第一个可运行闭环，用真实使用证据决定后续三级是否、以及以何种规模推进。Plan-as-Data 的主张值得做，但应该以它自己倡导的方式去做：一个工作项一个工作项地 claim，而不是一次灌入整份 3000 行的蓝图。
