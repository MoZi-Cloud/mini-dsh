# mini-DSH Design and Implementation Review and Recommendations v1.1

English | [中文](评审及改进建议.zh.md)

## Summary

The current source implements a reusable Project Ledger core: plan parsing and import, adjacent SQLite migrations, work-readiness computation, exclusive leases, and rebuildable WorkPackets all have explicit implementations. Two issues keep it from being a trustworthy automated execution loop: the model can declare an acceptance PASS directly in tool input, while the code neither executes the stored verifier nor compares expectations such as `expected_exit_code`; plan activation has no formal write operation, and `plan/version-activated` has neither payload validation nor replayed state. `dsh --profile mini` only reads and claims work from an existing ledger, so a user cannot import and activate a new plan through the supported entry point. v1.6d delivered collaboration records and claim visibility as specified by its narrowed proposal, so that limitation is not an implementation defect; claim authorization, path-conflict blocking, and full multi-agent scheduling need a separate decision once the trustworthy execution loop and external-task evidence are in place.

## 1. Review scope, version, and decision rules

The review covers the [original v1.6 proposal](HISTORY/fork-mini-DSH改造方案-v1.6.md), [narrowed v1.6a proposal](v1.6a/fork-mini-DSH改造方案-v1.6a.md), [SQLite Ledger Core appendix](v1.6a/fork-mini-DSH-v1.6a-SQLite核心账本附件.md), [v1.6b completion report](v1.6b/fork-mini-DSH-v1.6b-completion-report.md), [v1.6d scope proposal](v1.6d/fork-mini-DSH-v1.6d-collaboration-scope-proposal.md) and [completion report](v1.6d/fork-mini-DSH-v1.6d-completion-report.md), the [real-use log](real-use-log.md), and the related package and benchmark source.

The task boundary excludes product-code builds, source type-checking, and code tests in this round; test counts, coverage, and persistent-ledger results in completion reports are reported evidence, not independently reproduced results from this review.

| Category | Meaning |
| --- | --- |
| Implementation deviation | Current source violates an explicit accepted safety, lifecycle, or supported product-entry requirement |

## 2. Critical corrections to the v1.0 review

Version 1.0 identified the central verifier, activation, replay-scope, collaboration-record, and benchmark-evidence gaps, but it mixed current defects, intentional exclusions, and optional future architecture. Version 1.1 makes the following corrections.

| v1.0 assessment | v1.1 correction | Basis for correction |
| --- | --- | --- |
| Classified the multi-transaction report directly as P0 | Downgrades it to a P1 recovery issue | Each lower-level write is atomic; the expired-lease reaper preserves terminal states or recomputes abandoned IN_PROGRESS items to READY/BLOCKED, so current evidence does not establish permanent corruption |
| Classified v1.6d's failure to constrain claim as a defect | Reclassifies it as a scope decision | The [v1.6d scope proposal](v1.6d/fork-mini-DSH-v1.6d-collaboration-scope-proposal.md) explicitly leaves readiness unchanged, adds only per-actor claim visibility in stage A, and leaves owner writes in library functions |
| Required a complete durable receipt immediately | Separates a minimum repair from a target design | The minimum is a trusted executor that computes the verdict and rejects a model-reported PASS; persistence requirements should decide whether a separate cross-session receipt entity is necessary |
| Froze schema v10 unconditionally | Replaces the freeze with conditional entry criteria | A new migration is not inherently wrong; reject it when a new domain bypasses P0 work, expands duplicate parity, or has no real consumer |
| Classified versioned plan source files as a definite defect | Reclassifies them as optional audit hardening | The database records source path/hash and Git retains earlier content; a content-addressed artifact is mandatory only when independent recovery without repository history is required |
| Embedded a commit hash and several drift-prone counts | Removes the hash and reduces hand-written inventories | Documentation rules assign exact versioning to Git history; current inventories should be queried from source and completion reports |
| Did not inspect the supported first-use flow | Adds a high-priority finding | mini-profile commands are all read-only and configuration accepts only a ledger path; benchmarks use library calls and direct SQL for import/activation |

Version 1.1 retains the two highest-priority v1.0 conclusions: automated acceptance results are not trustworthy, and the plan lifecycle is not governed by a formal writer and complete replay.

<a id="overall-conclusion"></a>

## 3. Overall conclusion

The current implementation is accurately described as an experimental project-ledger core, work-claiming tools, and collaboration audit records. It can query, claim, record evaluations, and read audit results from a pre-populated ledger, but it cannot create that ledger through a supported entry point or establish that a PASS for an automatic criterion came from compliant execution of its stored verifier.

| Review area | Assessment | Category | Priority | Confidence |
| --- | --- | --- | --- | --- |
| Plan parsing, compilation, and transactional import | Solid implementation suitable for reuse | — | Retain | High (A) |
| SQLite versioning and lease concurrency | Key invariants are explicit | — | Retain | High (A) |
| Automated acceptance truth | Model input can declare PASS and stored expectations are not checked | Implementation deviation | P0 | High (A) |
| Activation and version replay | No formal activation writer; required event has no decoder/fold | Implementation deviation | P0 | High (A) |
| Supported first-use flow | Profile has no import/activate operation | Implementation deviation | P1 | High (A) |
| Interrupted report recovery | Lease expiry recovers, but one attempt lacks idempotent commit semantics | Maintenance risk | P1 | Medium-high (A/B) |
| v1.6d collaboration behavior | Matches the narrowed proposal; it is not a claim-authorization system | Scope decision | Decision item | High (A/C) |
| 4K and real-use evidence | Establishes budget pre-checking and integration paths, not product effectiveness by itself | Evidence gap | P2 | High (A/C) |
| Service and parity organization | Low-level database access and duplicated comparison logic increase change cost | Maintenance risk | P2 | High (A) |

The project should repair the two P0 findings before adding the supported import/activate path. External-task effectiveness and real consumers should decide whether to strengthen multi-agent scheduling, add tables, or enter v1.6c.

<a id="implementations-to-retain"></a>

## 4. Implementations to retain

These areas already have clear behavior owners. Improvements should extend their public operations instead of replacing them.

### 4.1 Strict plan input and transactional import

[YAML parsing](../../packages/experimental/project-ledger/src/parse-plan.ts), [schema validation](../../packages/experimental/project-ledger/src/plan-schema.ts), [semantic validation](../../packages/experimental/project-ledger/src/plan-semantics.ts), and [plan compilation](../../packages/experimental/project-ledger/src/plan-compile.ts) handle input in separate stages. [Plan import](../../packages/experimental/project-ledger/src/plan-import.ts) writes the immutable version, work items, and corresponding events in a transaction. Unknown fields, invalid references, and unsupported schemas do not depend on later execution for rejection.

### 4.2 Adjacent SQLite migrations and fail-closed behavior

The [SQLite schema](../../packages/experimental/project-ledger-sqlite/src/schema.ts) uses STRICT tables, foreign keys, partial unique indexes, monotonic `user_version`, and an adjacent-migration registry. Improvements must append migrations rather than rewrite committed generations.

### 4.3 Lease exclusion and interruption recovery

The [lease implementation](../../packages/experimental/project-ledger/src/lease.ts) recomputes readiness, handles stale leases, appends the event, and inserts a new lease inside `BEGIN IMMEDIATE`, with a partial unique index as the final arbiter. The database stores only the bearer-token hash; expiry and the reaper recover when a process loses the in-memory token. The reaper preserves VERIFYING and terminal states and recomputes an abandoned IN_PROGRESS item to READY/BLOCKED, which is why v1.1 no longer classifies the multi-transaction report directly as P0.

### 4.4 Rebuildable WorkPackets

The [WorkPacket implementation](../../packages/experimental/project-ledger/src/work-packet.ts) records a deterministic recipe, references, and hashes, and supports rebuilding and drift detection. This mechanism serves the project goal better than injecting the full Master Plan into every context and already supplies identifiers that can bind a verifier to a packet, plan version, and code baseline.

### 4.5 Plugin extension points

The [mini profile](../../packages/experimental/mini-profile/) adds neither a standalone Node application nor agent-loop changes. Activation, the verifier consumer, and owner commands should remain in the profile/plugin composition rather than add a package bin or a second workflow runtime.

<a id="main-findings"></a>

## 5. Main findings and recommendations

This section separates source facts, their relationship to the proposal, risk, and recommendations. Each finding first gives the minimum repair required by the accepted proposal, followed by a target design that may need added persistence or a product decision.

### 5.1 F-01 / P0: Untrusted input determines automated acceptance

#### Source facts

[evaluateAcceptanceCriterion](../../packages/experimental/project-ledger/src/acceptance.ts) defines the result as caller-reported and maps `PASS` directly to PASSING. `verification_ref` is optional, and the function does not read the corresponding `verification_specs` to check verifier kind, command, query, expected exit code, or expected JSON.

[project_work_update report](../../packages/experimental/mini-profile/src/project-work.ts) lets the model submit `{criterionId, result, exitCode?, outputTail?}`. `result` determines criterion status; `exitCode` and `outputTail` are optional observations. A caller can submit `PASS` without an exit code or submit `PASS` with a failing exit code, and the current code does not compare `expected_exit_code`.

`isAgentObservable` checks only whether a verifier has `command_text` or `query_text`; it neither executes COMMAND/TEST nor interprets SQL_ASSERTION/GRAPH_ASSERTION expectations. `sandbox_required` and `approval_required` enter storage and the WorkPacket, but the report path does not check them.

The [real-use worker](../../benchmarks/real-use/run-real-use.worker.ts) executes commands through `spawn('sh', ['-c', command])` and reports the result through the shipped tool. This lane shows that the tool can record an external result, but it bypasses the structured sandbox result from `ctx.shell` and runtime `ctx.approval`; it also cannot make the product tool reject a fabricated PASS.

#### Relationship to the proposal

[v1.6a §18](v1.6a/fork-mini-DSH改造方案-v1.6a.md#18-verifier-信任边界) requires COMMAND/TEST execution through the existing shell, sandbox, and approval path and forbids Project Ledger from running commands directly or bypassing policy. The ledger package correctly does not execute commands, but no consumer supplies a trusted execution chain, leaving a gap between “the ledger does not execute” and “the system verifies.”

Two approval concepts must remain distinct: the v1.6b ledger `approvals` rows are project-decision records, while runtime `ctx.approval` authorizes one tool execution. `verification_specs.approval_required` should map to the latter; a project approval row cannot substitute for runtime permission.

#### Minimum repair

1. Name the existing write a reported evaluation; a model-reported result cannot move COMMAND, TEST, SQL_ASSERTION, or GRAPH_ASSERTION automatically to PASSING.
2. Add a trusted verifier consumer to the mini profile. It reads the spec from the ledger and computes the verdict without accepting `result` from the model.
3. Execute COMMAND/TEST through `ctx.shell.resolve()` and `ctx.shell.run()`, and evaluate exit code, timeout, abort, sandbox denial, and runner failure. When `sandbox_required` is true, missing sandbox facts must fail closed.
4. When `approval_required` is true, call runtime `ctx.approval` from the owning Agent's open turn; the approval service requires audit within that turn, so a sessionless background script cannot fabricate permission.
5. Keep SQL_ASSERTION/GRAPH_ASSERTION ineligible for automatic completion without a trusted interpreter; accept OWNER_CONFIRMATION only through an owner operation.

#### Target design

If evidence must support independent cross-session audits, add a stable verification run/reference bound to the criterion, spec-content hash, plan version, WorkPacket or repository baseline, execution policy, and structured result. If existing events and evaluations can retain all of these facts, reuse them instead of adding an entity only to introduce the name “receipt.”

### 5.2 F-02 / P0: Plan activation lacks an authoritative writer, and its required event is neither validated nor replayed

#### Source facts

[Plan import](../../packages/experimental/project-ledger/src/plan-import.ts) correctly creates a DRAFT version, but no `activatePlanVersion` exists. The [context-light worker](../../benchmarks/context-light/run-4k.worker.ts), [real-use worker](../../benchmarks/real-use/run-real-use.worker.ts), and tests use direct SQL to move a version to ACTIVE; the real-use update does not set `activated_at_ms`.

[PROJECT_EVENT_TYPES](../../packages/experimental/project-ledger/src/project-events.ts) lists `plan/version-activated` as a required event, but the replay switch has no matching case or payload decoder. The event reaches the default branch without checking `activatedBy` or the target version; the current test deliberately uses it as a registered term with no projection effect.

`ReplayedPlanVersion` excludes status, activation/supersede timestamps, and the current-version pointer. [Project replay](../../packages/experimental/project-ledger/src/project-replay.ts) and [doctor](../../packages/experimental/project-ledger/src/doctor.ts) therefore cannot detect direct changes to these lifecycle fields. Supersede has a formal writer, but replay still does not rebuild the complete version lifecycle.

#### Relationship to the proposal

[v1.6a §8](v1.6a/fork-mini-DSH改造方案-v1.6a.md#8-plan-导入不是激活) requires activation to be an explicit owner action, and BOOT-04 requires replayed project events to equal the current projection. The W00–W12 breakdown does not assign a work package to an activation writer, so the accepted proposal and its implementation checklist are themselves incomplete; this is not merely an omitted implementation function.

#### Minimum repair

1. Define an owner-authorized activation operation that validates DRAFT state, active-version constraints, and import diagnostics in one transaction, then updates status, `activated_at_ms`, and `plans.current_version_id` and appends a strict `plan/version-activated` event.
2. Add an activation-event payload decoder. A required event must validate references and payload even if it temporarily has no fold effect; preferably, include version status and the current pointer in the fold itself.
3. Give supersede-plus-activation composition one owner. If a version switch requires both operations to succeed, provide an atomic switch operation; if a plan may temporarily have no ACTIVE version, document that state for callers.
4. Make benchmarks and test fixtures establish ACTIVE state through the formal operation instead of direct lifecycle-column updates.

#### Target design

The replayed projection includes version status, activation timestamp, supersede timestamp, and each plan's current version. Replay audit reports any direct SQL mutation. If the team decides that lifecycle fields are outside event reconstruction, it must narrow BOOT-04 and completion-report claims and retain independent database constraints plus doctor checks; it cannot continue to claim complete current-projection replay.

### 5.3 F-03 / P1: The supported mini profile cannot create its first usable ledger

#### Source facts

[MiniProjectLedger](../../packages/experimental/mini-profile/src/index.ts) configures only ledger path and busy timeout, and the service only opens the database. The [`/project` commands](../../packages/experimental/mini-profile/src/commands.ts) are explicitly read-only and have no import, activate, or supersede operation. The `project_work_*` tools assume that the database already contains an ACTIVE plan and claimable work.

Benchmark workers in the repository can establish state with `importPlanVersion`, `supersedePlanVersion`, and direct SQL. An ordinary user cannot complete “plan.yaml → import DRAFT → owner review → activate → claim” through the supported `dsh --profile mini` entry point.

#### Relationship to the proposal

[v1.6a §4](v1.6a/fork-mini-DSH改造方案-v1.6a.md#4-应用入口禁止独立-mini-dsh-node-bin) defines `dsh --profile mini` as the only product entry point and lists `/project import` as a preferred human-facing interface. The library capability exists, but the product entry point does not expose it.

#### Recommendation

Add owner-only `/project import <plan-path>`, `/project activate <version>`, and any required `/project supersede` operations, or an equivalent owner flow in the GUI. Import only parses, validates, and writes DRAFT; it never executes a verifier. Activate presents diagnostics, baseline, and target version and requires an explicit owner action. Every entry point calls the same F-02 service operation, duplicates no SQL, and adds no package bin.

### 5.4 F-04 / P1: A report lacks idempotent commit semantics for one attempt

#### Source facts

`project_work_update report` first sends a heartbeat, then commits each evaluation, moves through VERIFYING/DONE/FAILED in separate operations, and finally releases the lease. Each step is atomic by itself, but one report has neither a shared transaction nor an operation id.

An interrupted process can leave some evaluations and an active lease. The current lease reaper recovers it after expiry: terminal states remain unchanged, while IN_PROGRESS recomputes to READY/BLOCKED. This is not evidence of permanent corruption and should not remain P0; its costs are recovery delay, duplicate evaluations, and uncertainty about how far the attempt committed.

#### Recommendation

Define the intended semantics before choosing the mechanism:

1. If a group of criterion verdicts and the status transition must become visible together, finish verifier execution outside the database transaction and submit all evaluations, the work status, and lease completion through one ledger operation in one `BEGIN IMMEDIATE`.
2. If incremental commits remain necessary, add an attempt/operation id and explicit stages so retries recognize completed steps and finish or terminate idempotently.
3. Inject failures at every write point and restart the process to verify immediate retry, waiting for the reaper, and duplicate-report outcomes; lower-level rollback tests alone are insufficient.

### 5.5 F-05 / P2: The ProjectLedger service abstracts at too low a level

[MiniProjectLedger](../../packages/experimental/mini-profile/src/index.ts) exposes `db: DatabaseSync`, and commands and work tools run SQL directly or call library functions that accept `DatabaseSync`. This is not a current behavior defect and does not justify an immediate rewrite merely for theoretical provider replacement. It does, however, prevent one stable service operation from owning activation, trusted verification, and atomic reporting, and it lets consumers recombine transaction semantics differently.

First promote the operations required by F-01 through F-04 to `ProjectLedger` service methods, then implement them in the SQLite provider. Drive migration by consumer needs, initially covering import/activate/switch, claim, verify/report, todo, and replay; read-only functions without a second consumer or transaction-ownership need can remain library APIs.

### 5.6 F-06 / Decision item: v1.6d delivered recordkeeping; scheduling constraints remain undecided

#### Current scope

The [v1.6d scope proposal](v1.6d/fork-mini-DSH-v1.6d-collaboration-scope-proposal.md) explicitly preserves existing readiness and todo computation while adding work assignments, handoffs, scope reservations, conflict records, and per-actor claim visibility. Current [claimWorkItem](../../packages/experimental/project-ledger/src/lease.ts) does not read assignments, handoffs, reservations, or conflicts, matching that narrowed scope.

A scope reservation excludes only an exactly matching `(project_id, scope_kind, scope_value)` tuple; conflict records, rather than reservations, cover parent/child path overlap. The completion report discloses this limitation, so it is known semantics rather than a hidden defect.

#### Later decision

If the product needs only collaboration audit and claim visibility, retain the current behavior and correct its documentation names without adding scheduling complexity. If real use requires the system to block unauthorized claims or overlapping paths, decide separately:

- the stable mapping from session agent to ledger actor;
- which assignment kinds authorize claim;
- whether handoff records activity or transfers claim authority;
- whether PATH reservations normalize paths and detect ancestor/descendant overlap;
- whether an open conflict becomes a readiness blocker.

Failures observed with two independent Agent sessions must drive these rules; the existence of tables alone does not justify enabling all of them.

### 5.7 F-07 / P2: Validation-lane evidence is weaker than the stage-entry conclusion

The [context-light README](../../benchmarks/context-light/README.md) accurately distinguishes deterministic and live lanes. The deterministic lane in the source uses private `project_work_*` fixtures, a scripted adapter, and a `ceil(bytes / 4) + 512` pre-check; only the explicitly selected live lane uses provider-reported usage. A keyless result therefore establishes the fixed sequence, request assembly, and estimated budget, not shipped mini-profile tool behavior or real-model task completion.

The [real-use README](../../benchmarks/real-use/README.md) also states that no model participates. Its lane uses shipped work tools and can establish persistent-ledger, claim/report, and read-audit integration; its direct verifier subprocess and fixed lane identity cannot establish model judgment quality, runtime permission enforcement, or multi-agent concurrency.

Retain the lanes and narrow the conclusions:

| Lane | Fact suitable for entry evidence | Conclusion it cannot support alone |
| --- | --- | --- |
| deterministic 4K | Fixed requests fit the heuristic budget; the full plan is not injected | Real tokenizer usage, model task success, or shipped-tool equivalence |
| live 4K | Reported input usage and real-model interaction for a fixed provider | General model effectiveness or multi-task reliability |
| shipped-profile integration | Shipped tools, SQLite, and state transitions work together end to end | Model autonomy or sandbox/approval compliance |
| external-task effectiveness | Success rate, tokens, and retries against a non-ledger-task baseline | Multi-agent concurrency unless independent sessions participate |
| multi-agent concurrency | Competition, handoff, and recovery between independent sessions | One process writing two identities sequentially is not this evidence |

Stage entry should include several non-Project-Ledger bootstrap tasks and a baseline without the ledger. Golden implementation work remains useful regression data but should not bear product-value confirmation alone.

### 5.8 F-08 / P2: Duplicate parity and current-state documentation drift increase expansion cost

[Doctor](../../packages/experimental/project-ledger/src/doctor.ts) and [project replay](../../packages/experimental/project-ledger/src/project-replay.ts) independently maintain projection comparisons across entity families, while [project-events.ts](../../packages/experimental/project-ledger/src/project-events.ts) owns most event types, decoders, and folds. A new domain must update several comparisons, and activation demonstrates that a registered event type can pass through the current organization without a decoder or fold.

Make `readProjectReplay` the sole owner of projection parity. Doctor converts drift into issues and adds only runtime health checks that replay cannot express. Split event decoders/appliers by domain behind an explicit registry; registering a required type must also supply a decoder and fold policy, without relying on a switch default.

Current package READMEs also drift: the [project-ledger README](../../packages/experimental/project-ledger/README.md) limitation still says “No activation or supersede yet,” although supersede exists; the [SQLite README](../../packages/experimental/project-ledger-sqlite/README.md) migration text stops at earlier generations; package descriptions still identify the current packages with v1.6a and the initial table count. Completion reports can freeze history, while READMEs and manifest descriptions should state current behavior and link historical reports.

Versioned plan source documents are optional hardening. If an audit must reconstruct old input independently of Git history, add version-named files or a content-addressed artifact; otherwise source hash, path, and repository history can remain the evidence set.

<a id="phased-proposal"></a>

## 6. Phased implementation proposal

The implementation order prioritizes closing incorrect states; it is not aimed at increasing the table count or version numbers.

### Phase A: Restore result truth and lifecycle authority

- Implement the trusted verifier consumer from F-01 so code computes an executable criterion verdict from its stored spec.
- Implement the activation/switch operation, strict activation-event decoder, and version-lifecycle replay from F-02.
- Label current caller-reported data as reported and stop treating it automatically as verified.
- Move benchmark direct-SQL activation and direct verifier spawning to formal operations; reports continue to disclose these limitations until then.

Exit condition: a fabricated PASS cannot make work DONE; every ACTIVE version traces to a valid activation event; audits detect direct lifecycle mutation.

### Phase B: Complete the supported entry path and interruption semantics

- Add owner import/activate/supersede flows to `dsh --profile mini`.
- Choose atomic reporting or an operation-id recovery protocol, and cover write-point failures.
- Give typed ProjectLedger service operations ownership of new transactions instead of composing SQL independently in commands, tools, and benchmarks.

Exit condition: a new user can create claimable work from a plan file using only the supported profile; every interrupted report has a deterministic, tested recovery result.

### Phase C: Consolidate duplicate implementation and validation evidence

- Consolidate replay/doctor projection-parity ownership and split event decoder/applier organization.
- Make deterministic 4K use shipped tools while continuing to report heuristic budgets separately from provider usage.
- Establish live-model comparisons on non-ledger repository tasks, recording success rates, token usage, retries, and human intervention.
- Correct current-state drift in READMEs and package descriptions.

Exit condition: a new event cannot register only its type while omitting decoder/fold policy; product-value conclusions no longer depend on bootstrap tasks or a keyless scripted Agent.

### Phase D: Decide whether to strengthen multi-agent scheduling or enter v1.6c

- First observe actual authorization, handoff, and scope-conflict failures between independent Agent sessions.
- Implement only the assignment, handoff, reservation, or conflict rules required by those cases.
- Keep v1.6c behind the signature/call-site extractor research criteria; declared intent does not become an automatic blocking fact.

Exit condition: each scheduling rule has a real failure case, one behavior owner, and comparison evidence without the rule.

<a id="final-assessment"></a>

## 8. Final assessment

The v1.6a core data model and lease design do not need replacement, and data recorded by v1.6b and v1.6d does not need rollback. The project should first repair two problems that change the meaning of facts: the system cannot currently establish PASS, and its events cannot establish which plan version was validly activated. It should then add owner write operations to `dsh --profile mini`, making the proposed vertical slice a supported flow that an ordinary user can complete for the first time.

Report atomicity, a typed service, and parity consolidation are the next recovery and maintenance items and should not be conflated with P0. The current v1.6d implementation matches its narrowed scope; “collaboration records and claim visibility” is its most accurate name.
