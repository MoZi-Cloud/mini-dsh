# Agent Note: The v1.6b Approval Domain

Status: implemented

English | [中文](2026-09-19-v1.6b-approval-domain.zh.md)

## Problem

The v1.6b plan's second item (blueprint attachment §24) brings approvals: an owner's approval hangs beside a typed subject — a plan version, a work item, or a decision — requested by one actor, decided by another, with the blueprint's one-line ruling that decisions and approvals never share a table. The domain inherits every constraint the decision domain set three constraints deep. The event format is now 2 with the adjacent-read contract, and adding the two required approval events must bump it again without invalidating the 118-event persistent timeline (97 rows stamped 1, 19 stamped 2). The physical schema is at version 2 with one frozen 1→2 step, so the approvals table arrives as exactly one appended 2→3 step. And the blueprint's own spec names `required_role_id` and content-id indirection that v1.6a never adopted, so the layout is an adaptation again. One modeling problem is new: an approval's deciding facts (`decided_by`, decision text, `decided_at_ms`) are optional as a group and mandatory as a group — the CHECKs the schema adds enforce exactly that coupling, and both the read seam and the `/project approvals` view have to expose it without inventing unreachable fallback branches.

## Decision

- **Schema v3 as one appended migration step (2 → 3)**: one `approvals` table — `subject_type` closed set `plan-version`/`work-item`/`decision`, `subject_id` validated to belong to the same project at write time, `required_role`/`requested_by`/`decided_by` actor strings, inline `decision_text`, status `PENDING`/`APPROVED`/`REJECTED` — with three CHECKs coupling the deciding columns to the non-PENDING status all-or-nothing, and its own indexes by project and by subject. No decision table gained a column; the ruling holds in the physical layout.
- **Event format 3 under the same adjacent-read contract**: `approval/requested` and `approval/decided` joined the required vocabulary; the decoder still rejects only rows stamped newer than the build, so the mixed 1/2 stamps on the persistent timeline stay readable beside the first format-3 rows.
- **Ids are timeline-derived like leases and evaluations**: `ap:<projectId>:<eventSequence>`, allocated by the pre-read inside the writer's `BEGIN IMMEDIATE`; approvals carry no natural key because the blueprint gives them none.
- **The deciding facts are one group in the read shape**: `readProjectApprovals` returns `decision: { decidedBy, decisionText, decidedAtMs } | undefined`, built on the single nullable `decided_by` with the sibling columns cast through the CHECKs' guarantee — the same trust the decision read places in its join. The view then renders the deciding line without fallbacks a valid row can never reach, and the per-file coverage gate stays honest.
- **Both enforcement layers validate the loop**: the write seams reject an unknown or foreign-project subject of any kind, an invalid outcome, and a decided approval (`an approval decides exactly once`); the replay fold additionally fails closed on a subject no replayed entity of that kind carries, an `approval/decided` naming an unreplayed approval, and a second decision on one approval. Parity compares subject reference, status, and deciding actor in both existing sweeps — `readProjectReplay` and the doctor's projection check — in both directions.
- **The §33 entry approval is the domain's first row**: after the lane completed the implementation item, a one-off script requested the approval over the v1.6b plan version (requiring the `owner` role, requested by the owner) and recorded the owner's APPROVED decision citing the §33 gate — the approval record of the gate that opened the domain, and the timeline's first format-3 rows.

## Alternatives considered

- **A polymorphic foreign key on the subject** — rejected: SQLite has no typed-union FK; the closed subject vocabulary with a per-kind same-project check at write time and per-kind existence in the fold carries the same guarantee with a smaller surface.
- **Keeping the deciding facts as three optional flat columns in the read shape** — rejected: the CHECKs make half-decided rows unreachable, so flat optionals forced either unreachable render fallbacks or uncovered branches; the grouped `decision` object states the coupling the schema already enforces.
- **A natural key for approvals (project + subject + role)** — rejected: the blueprint gives approvals no UNIQUE constraint, and repeated approvals of one subject are legitimate (request again after a REJECTION); the timeline-derived id matches the lease and evaluation precedent.
- **`approval/recorded` as the second event name** — rejected: the event records the outcome of a decision on the approval; `approval/decided` names the act, and the seam pair reads `requestApproval`/`decideApproval`.
- **Folding approvals into the decisions tables** — rejected: the blueprint's one-line ruling ("Decision 与 Approval 不共表") is explicit, and the separation kept the decision domain's migration and parity untouched.

## Consequences

- The event format and the physical schema both reached 3; any future required vocabulary addition or layout change appends one more adjacent step and inherits the older-stamps-decode contract.
- The persistent ledger now folds a 1/2/3 mixed-stamp timeline clean (97/19/2 rows over 118 events) — the seven format-2 rows this increment's lane run wrote came from the previously built surface before the rebuild, their stamps truthful about their writers; the audit reads all three.
- The v1.6b plan is complete in its first two items; actors/roles basic expansion and the resource domain (requirements/instances/verifications, blueprint §25–27) remain, and the read-only `/project approvals` view is the surface a future interactive owner writer extends.
- Approvals over work items give the `work_external_blockers` `APPROVAL` blocker kind a durable place to point: resolving an APPROVAL blocker can now mean a decided approval row beside the blocked item.
