# Agent Note: The v1.6d Work-Assignment Domain

Status: implemented

English | [中文](2026-09-20-v1.6d-work-assignment-domain.zh.md)

## Problem

Stage A of the v1.6d collaboration scope opens with work assignments (blueprint §18): an actor's duty on one work item, the missing piece of the §1 family line "actors / roles / assignments" — v1.6b shipped the project-scoped `actor_roles`, not this table. The domain inherits the now-five-layer structure: the schema is 5 with five frozen steps, so the table lands as exactly one appended 5→6 step; the event format is 5 with 24 required events, and the new required event must bump it without invalidating the persistent timeline's 97+19+2+14+15 mixed stamps (147 events). The blueprint's own idioms need the usual adaptation, and one question it leaves open has real forward cost: which of the six `assignment_kind` values to close on, since extending a CHECK later costs another migration step.

## Decision

- **Schema v6 as one appended migration (5 → 6)**: one `work_assignments` table — `work_item_id`, `actor_id`, nullable `role_id` referencing the v1.6b `actors`/`roles` rows directly (the blueprint's foreign keys became real when those referents shipped, so no actor-string adaptation is needed here), `assignment_kind` closed to the blueprint's six values uppercased (`PRIMARY`/`COLLABORATOR`/`REVIEWER`/`TESTER`/`OBSERVER`/`ACCOUNTABLE`), `status` closed to `ACTIVE`/`ENDED`, `assigned_at_ms`, and reserved nullable `accepted_at_ms`/`completed_at_ms`. No `project_id` column: the item's project scopes the row, exactly like the shipped `work_leases`. The item and actor indexes cover the blueprint §57 "assignments actor/status" query requirement.
- **The PRIMARY duty is singular**: the partial unique index `uq_one_live_primary_per_work(work_item_id) WHERE status = 'ACTIVE' AND assignment_kind = 'PRIMARY'` and the seam both refuse a second, and the replay fold re-checks it over the replayed assignments — one primary executor per item is a database fact that mirrors the lease invariant (`uq_one_active_lease_per_work`) without merging the two concepts: the lease owns an item's execution, the assignment records its duty structure.
- **Event format 6 under the adjacent-reads contract**: `work/assigned` joins the required vocabulary; ids `wa:<projectId>:<eventSequence>` timeline-derived, because ending a PRIMARY (the reserved future writer) must permit re-assignment. The payload carries ids, never keys — the fold resolves item, actor, and role through its projection maps, and a second-PRIMARY check over the fold's live map mirrors the index the same way `role/assigned` mirrors its pair index.
- **`WORK_ASSIGNMENT_KINDS` is owned by the event codec** (`project-events.ts`, the `ResourceVerifierKind` lesson): the write seam validates against the same closed set the decoder enforces, so a kind can never exist in one and not the other.
- **The read resolves labels through joins**: `readProjectWorkAssignments` returns newest-first assignments carrying the item's `stableKey`, the actor's `actorKey`, and the role's `roleName` — the actor-domain pattern that keeps view-side fallback branches unreachable and the coverage gate honest. The reserved `accepted_at_ms`/`completed_at_ms` columns are deliberately absent from the read shape until a writer exists (the grouped-decision precedent).
- **Stage granularity deviates from the proposal's wording**: the scope proposal sketched stage A as one migration carrying assignments and handoffs; the plan yaml (born this increment, `docs/mini/v1.6d/fork-mini-DSH-v1.6d.plan.yaml`) splits stage A into one domain per item so every migration step ships married to its writer — no table exists an increment before its events. Handoffs take step 6→7 next; per-actor claim visibility needs no schema change.
- **The domain's first rows point forward**: `wa:mini-dsh:159` assigns the lane `PRIMARY` (as `executor`) on `PA-HANDOFF-RECORD-001` and `wa:mini-dsh:160` assigns `owner` `ACCOUNTABLE` on it — the duty structure of the work that will actually claim the item, recorded as events 159–160, the timeline's first format-6 stamps.

## Alternatives considered

- **One 5→6 migration carrying assignments and handoffs together** (the proposal's wording) — rejected: it would ship the handoffs table a full increment before its events, leaving a permanently possible empty table if stage B or the evidence redirects; the plan yaml records the deviation.
- **A smaller `assignment_kind` start (PRIMARY/COLLABORATOR only)** — rejected: extending a CHECK vocabulary costs another migration step, and the blueprint's six duties are all plausible for this ledger (owner as `ACCOUNTABLE`, reviews as `REVIEWER`); closing all six now is the forward-compatible choice.
- **Actor strings over actor ids (the v1.6b adaptation)** — rejected: that adaptation existed because the actor tables didn't; they do now, so the blueprint's foreign keys ship as written and the fold resolves every reference through `requireReplayedActor`/`requireReplayedRole`.
- **A fold-level uniqueness rule without a schema index** — rejected: the actor-domain rule became a database fact via its partial unique index; a fold-only rule would be a weaker copy. The one-live-PRIMARY rule ships as index + seam + fold, all three.
- **Exposing `accepted_at_ms`/`completed_at_ms` in the read shape** — rejected: with no writer, every render branch over them would be unreachable (the grouped-decision precedent); the read shape gains them when the writer does.

## Consequences

- The v1.6d stage-A batch is one-third done: `PA-HANDOFF-RECORD-001` (schema 6→7, format 7) and `PA-CLAIM-VISIBILITY-001` (no schema change) remain, and the assignment rows recorded now are the duty structure those increments execute against.
- The persistent ledger folds a six-stamp timeline in place (97+19+2+14+15+13 over 160 events after this increment's runs); any future required vocabulary addition bumps the format again under the same adjacent-reads contract.
- The `ACCOUNTABLE` assignment gives the owner's go-gate duty a row beside the executor's claim, which the per-actor claim visibility item can project directly.
