# Agent Note: The v1.6b Resource Domain

Status: implemented

English | [中文](2026-09-19-v1.6b-resource-domain.zh.md)

## Problem

The v1.6b scope's third family (blueprint attachment §25/§26/§27) brings resources: a project opens resource requirements, instances are provided against them, and each instance is verified against a spec. The blueprint's three tables carry the same v1.6a-foreign idioms as the decision and approval tables — `UNIQUE(plan_version_id, requirement_key)` with its NULL-distinct trap, `content_id` indirection, actor ids — so the layout is again an adaptation. The structural constraints have now compounded three deep: the event format is 3 with adjacent reads and the three new required events must bump it to 4 without invalidating the persistent timeline's 97+19+2 mixed stamps; the schema is at 3 with three frozen steps, so the resource layout arrives as exactly one appended 3→4 step. Two new modeling questions arose. Where does `verifier_kind` live — the acceptance vocabulary owns a type with the same five values, but importing the plan-document type into the resource seam repeats the catalog collision this tree already learned from? And how far does the lifecycle go — the blueprint gives requirements and instances status columns but no writers for their transitions?

## Decision

- **Schema v4 as one appended migration step (3 → 4)**: `resource_requirements` (project-scoped `UNIQUE(project_id, requirement_key)`, required JSON-object `constraints_json`, status `OPEN`/`FULFILLED`/`CANCELLED`), `resource_instances` (requirement reference, JSON-object `metadata_json`, status `AVAILABLE`/`RETIRED`), and `resource_verifications` (instance reference, the five-kind `verifier_kind` CHECK, inline `verification_spec`, `observed_json`, `PASS`/`FAIL`), each with its project/reference index. No blueprint table gained a column from another family.
- **Reserved statuses are honest**: `FULFILLED`, `CANCELLED`, and `RETIRED` are CHECK-legal with no writer; the `provideResourceInstance` seam refuses non-OPEN requirements so the reserved states stay unreachable until their writers land, and the README limitation names them. This is the `REVOKED`-lease precedent.
- **Event format 4 under the same adjacent-read contract**: `resource/required`, `resource/provided`, and `resource/verified` joined the required vocabulary; older stamps decode, newer stamps fail closed. Ids follow the house derivations: `rr:<projectId>:<requirementKey>` by identity, `ri:` and `rv:` timeline-derived like leases and approvals.
- **The verifier-kind vocabulary moved into the codec, renamed**: `RESOURCE_VERIFIER_KINDS` (the same five values as the acceptance kinds) is owned by `project-events` with a resource-specific reader and error text, and the resource seam uses `ResourceVerifierKind` — never the plan-document type. Exporting an equivalently-named public type already made the cordis catalog silently drop a `dsh-user-approval` entry once; the resource domain keeps its own name so the catalog stays whole and the codec owns what it validates.
- **JSON-text fields are validated at the parser seam**: `constraintsJson`, `metadataJson`, and `observedJson` must parse as JSON objects when present; the read seam stores and returns the raw text so the view shows the facts as written.
- **Re-verification is legal, by design**: each `resource/verified` event records its own row and timeline-derived id; an instance may be verified repeatedly as its facts change, mirroring acceptance evaluations.
- **Parity covers all three families, both directions**: requirements by identity facts (key, kind, name) and status; instances by their requirement reference and status; verifications by their instance reference and result — in `readProjectReplay` and the doctor's projection sweep alike.
- **The domain's first row is a real resource**: after the lane run, a scratch script recorded the persistent ledger file itself as the domain's first requirement (`rr:mini-dsh:persistent-ledger`, raised against the v1.6b plan version), its file as the provided instance, and the replay audit that had just folded the timeline clean as its PASS verification — ledger evidence about the ledger's own substrate.
- **The plan superseded itself for real**: importing version 2 of `mini-dsh-v16b-owner-decision` drove the §22 freeze of version 1 through the lane's existing supersede-then-activate path; version 2 lists only fresh stable keys.

- Migration coverage: a real v3 database (all shipped steps, one approval row, stamped 3) upgrades through 3→4 with rows intact; the committed v1 fixtures upgrade through all four steps on copies; the registry contiguity test holds with four steps.
- Format coverage: a format-5 row rejects with `this build reads up to format 4`; payload validation covers every field of the three events, including kind and result membership, optional-string typing, and per-family existence in the fold.
- Parity coverage: materialized-only and replayed-only ghosts for all three families, identity-fact, reference, status, and result disagreements in both the audit and the doctor, with exact finding texts and the collectors' push order pinned.
- Gates: oxlint 0/0, duplication back at the standing two-clone baseline (an identical import block between doctor and replay was broken by reordering one side), translation pairing re-recorded for every edited bilingual pair, doc gates 20/20.
- Lanes: temp first-try green on the fresh v2 import; the persistent run superseded version 1, completed `PB-RESOURCE-RECORD-001`, and migrated 3→4 in place; the idempotent rerun on the rebuilt surface passed with zero tool calls; the 4K slice stayed green (max 2,444/4,096). The persistent timeline folds 97+19+2+14 stamps across formats 1–4 (132 events) clean.

## Alternatives considered

- **Reusing `PlanAcceptanceKind` for the resource verifier kind** — rejected: the zod-derived type crosses the resource seam's `.run()` calls (type-safety lint) and a same-named export already dropped a catalog entry once; the codec owning `RESOURCE_VERIFIER_KINDS` keeps the values identical, the names distinct, and the validation local.
- **Writing the lifecycle transitions now** (`FULFILLED`, `CANCELLED`, `RETIRED`) — rejected: no consumer drives them, and an event without a caller is a vocabulary entry the fold must defend forever; the CHECKs admit them, the seams refuse them, and the writers land with the first consumer.
- **A join query for `readProjectResources`** — rejected: three families nest two deep and the LEFT JOIN fan-out would repeat the decision read's regrouping with a third level; three ordered queries and two Maps keep the nesting explicit and the rows single-purpose.
- **A natural key for instances and verifications** — rejected: neither the blueprint nor any consumer names one; repeats are legitimate (re-request, re-verify), so both ids derive from their events' sequences like leases and approvals.
- **Separate requirement/instance/verification view commands** — rejected: the three families read as one answer ("what does this project need, what serves it, does it hold"); one `/project resources` view renders the nesting and the parse step stays closed.

## Consequences

- The event format and the physical schema both reached 4; the adjacent-step discipline now spans four steps and the committed fixtures exercise all of them on every suite run.
- The persistent ledger folds formats 1–4 beside each other (97+19+2+14 over 132 events) — the mixed-stamp timeline is now the normal state, not an edge case.
- The v1.6b plan runs on version 2 with `PB-ACTOR-ROLE-001` (actors and roles as first-class rows) READY — the last family of the proposal's v1.6b scope; it gives `required_role` and every actor string a durable referent.
- Resource requirements give owner-facing evidence a third shape: a requirement names what the project needs, the instance names what answers it, and the verification names how it was checked — all folded, audited, and viewable without SQL.
