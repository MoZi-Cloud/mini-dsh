# Agent Note：v1.6d 工作指派域

Status: implemented

[English](2026-09-20-v1.6d-work-assignment-domain.md) | 中文

## 问题

v1.6d 协作范围的阶段 A 以工作指派开篇（蓝图 §18）：一个 actor 在一个工作项上的职责——§1 家族行 "actors / roles / assignments" 里缺的那块，v1.6b 交付的是项目级 `actor_roles`，不是这张表。本域继承如今已五层深结构：schema 是 5、带五个冻结步骤，所以这张表恰好以一次追加的 5→6 步落地；事件格式是 5、带 24 个 required 事件，新增的 required 事件必须升版而又不使持久时间线里 97+19+2+14+15 的混合戳失效（147 事件）。蓝图自身的惯用法仍需照例适配，而它留白的一个问题有真实的前向成本：六个 `assignment_kind` 值闭合到哪几个——之后扩展 CHECK 词表要再付一次迁移步骤。

## 决策

- **Schema v6 作为一次追加迁移（5 → 6）**：一张 `work_assignments` 表——`work_item_id`、`actor_id`、可空 `role_id` 直接引用 v1.6b 的 `actors`/`roles` 行（当那些指向物交付后，蓝图的外键就成了真的，这里不需要 actor 字符串适配），`assignment_kind` 闭合到蓝图六值的大写（`PRIMARY`/`COLLABORATOR`/`REVIEWER`/`TESTER`/`OBSERVER`/`ACCOUNTABLE`），`status` 闭合到 `ACTIVE`/`ENDED`，`assigned_at_ms`，以及预留的可空 `accepted_at_ms`/`completed_at_ms`。无 `project_id` 列：条目的项目给行定界，与已交付的 `work_leases` 完全一致。item 与 actor 索引覆盖蓝图 §57 的 "assignments actor/status" 查询要求。
- **PRIMARY 职责单一**：部分唯一索引 `uq_one_live_primary_per_work(work_item_id) WHERE status = 'ACTIVE' AND assignment_kind = 'PRIMARY'` 与接缝都拒绝第二条，replay fold 在重放的指派上重查同一规则——每项一个主执行者是数据库事实，镜像租约不变式（`uq_one_active_lease_per_work`）而不合并两个概念：租约拥有条目的执行，指派记录条目的职责结构。
- **事件格式 6 在相邻读取契约下**：`work/assigned` 加入 required 词表；id `wa:<projectId>:<eventSequence>` 按时间线派生，因为结束一个 PRIMARY（预留的未来写入者）必须允许再指派。payload 携带 id、不携带键——fold 经其投影映射解析 item、actor、role，fold 活跃映射上的第二条 PRIMARY 检查镜像索引，正如 `role/assigned` 镜像其配对索引。
- **`WORK_ASSIGNMENT_KINDS` 由事件编解码器拥有**（`project-events.ts`，`ResourceVerifierKind` 的教训）：写入接缝与解码器校验同一闭合集，kind 不可能在一侧存在而另一侧没有。
- **读取经 join 解析标签**：`readProjectWorkAssignments` 按最新在前返回携带条目 `stableKey`、actor `actorKey`、role `roleName` 的指派——actor 域模式，让视图侧回退分支保持不可达、覆盖率门保持诚实。预留的 `accepted_at_ms`/`completed_at_ms` 列在写入者出现前刻意不进读取形状（分组 decision 先例）。
- **阶段粒度偏离提案措辞**：范围提案把阶段 A 画成一次迁移同时承载指派与交接；随本增量诞生的计划 yaml（`docs/mini/v1.6d/fork-mini-DSH-v1.6d.plan.yaml`）把阶段 A 拆成每条目一域，让每个迁移步骤与自己的写入者同批交付——不让任何表在其事件出现前一个增量就存在。交接下一步走 6→7；按 actor 的领取可见性不需要 schema 变化。
- **本域首批行指向前方**：`wa:mini-dsh:159` 把 `PRIMARY`（以 `executor` 角色）指给 lane 在 `PA-HANDOFF-RECORD-001` 上，`wa:mini-dsh:160` 把 `owner` 的 `ACCOUNTABLE` 指在同一条目上——即将真实领取该条目的工作的职责结构，记为事件 159–160，时间线的首批 format-6 戳。

## 验证

- 三个包（`project-ledger`、`project-ledger-sqlite`、`mini-profile`）共 330 个测试，per-file 100% 覆盖率；账本条目的存储 verifier 正是这条三包命令。
- 迁移覆盖：真实 v5 数据库（全部已交付步骤、一行 actor、戳 5）带行升级通过 5→6；入库的 v1 fixtures 就地升级通过全部六步；注册表连续性测试在六步下成立；裸 SQL 测试钉住部分唯一索引、CHECK 词表与三个外键。
- 格式覆盖：比构建更新的戳以 `this build reads up to format 6` 拒绝；旧格式行仍可解码；`work/assigned` 每个字段有 payload 校验，含 kind 词表、fold 的 item/actor/role 存在性检查与第二条 PRIMARY 拒绝。
- Parity 覆盖：物化有/重放有的双向幽灵，actor/item、role、kind、status 不一致，在审计与 doctor 两处，均钉住精确 finding 文本与收集器推入顺序。actor-role 有效期 drift 消息里既有的不可达分支（fold 把每条指派重放为活跃期间不可达）已通过去掉死条件来消除。
- 门：oxlint 0/0，duplication 站在既有两 clone 基线，每个改动的双语对已重录 pairing，文档门绿。
- Lane：持久运行经存储 verifier 完成 `PA-WORK-ASSIGNMENT-001`，账本首次打开时就地迁移 5→6；幂等重跑零工具调用通过；4K 切片保持绿色（最大 2,444/4,096）；首批行落库后 replay 审计 0 drift、doctor 0 issues。

## 落选的备选

- **一次 5→6 迁移同时承载指派与交接**（提案措辞）——拒绝：它会让 handoffs 表在其事件出现前整整一个增量就存在，若阶段 B 或证据转向，留下一个永远可能为空的表；计划 yaml 已记录该偏离。
- **更小的 `assignment_kind` 起步（仅 PRIMARY/COLLABORATOR）**——拒绝：扩展 CHECK 词表要再付一次迁移步骤，而蓝图六种职责对本账本都真实可期（owner 的 `ACCOUNTABLE`、评审的 `REVIEWER`）；现在闭合全部六值是前向兼容的选择。
- **actor 字符串代替 actor id（v1.6b 式适配）**——拒绝：那项适配存在于 actor 表缺席之时；如今它们在，蓝图外键按原样交付，fold 经 `requireReplayedActor`/`requireReplayedRole` 解析每个引用。
- **无 schema 索引的 fold 级唯一规则**——拒绝：actor 域规则经部分唯一索引成为数据库事实；仅 fold 的规则只是更弱的副本。一条活跃 PRIMARY 规则以索引 + 接缝 + fold 三层交付。
- **把 `accepted_at_ms`/`completed_at_ms` 暴露进读取形状**——拒绝：没有写入者时，其上的每个渲染分支都不可达（分组 decision 先例）；写入者落地时读取形状随之增列。

## 后果

- v1.6d 阶段 A 批次完成三分之一：`PA-HANDOFF-RECORD-001`（schema 6→7、format 7）与 `PA-CLAIM-VISIBILITY-001`（无 schema 变化）待做，而此刻记录的指派行正是这些增量要执行的职责结构。
- 持久账本就地折叠六戳时间线（本增量运行后 160 事件中 97+19+2+14+15+13）；未来任何 required 词表新增按同一相邻读取契约再次升版。
- `ACCOUNTABLE` 指派让 owner 的 go 门职责在执行者的领取旁边拥有一行，按 actor 的领取可见性条目可以直接投影它。
