# Agent Note：v1.6d 协作冲突域

Status: implemented

[English](2026-09-20-v1.6d-collaboration-conflict-domain.md) | 中文

## 问题

v1.6d 协作范围以协作冲突收拢阶段 B（蓝图 §29）：记录一次从范围预留漏掉的撞界——等值唯一性检查只判等值路径，两条已预留路径仍可因包含关系相撞。域继承如今的八层结构：schema 为 8、冻结八步，故表以恰好一条追加的 8→9 步落地；事件格式为 8、29 个必需事件，压在 195 条事件的持久时间线上。蓝图表照例需要适配，两个问题塑造本域：一条冲突的最小诚实内容是什么，以及由什么收拢它。

## 决策

- **Schema v9 以一条追加迁移落地（8 → 9）**：一张 `collaboration_conflicts` 表——删去 `project_id`（经第一个工作条目行派生，与工作指派、交接两表同理；此处不存在项目级唯一性谓词），外键直指两条工作条目行、actor 行与 decisions 行，蓝图的 `description_content_id` 间接引用内联为 description 文本，可空的 `raised_by_actor_id` 与工作条目列收口为必填。接缝拒绝条目与自身的冲突：冲突记录的是两条相撞的工作流，不是同一条被报告两次。
- **`conflict_kind` 收口为 `SCOPE_OVERLAP`**：蓝图未给该列定值；本账本预留无法阻止的唯一撞界，是两条已预留仓库路径按包含关系重叠——等值检查判不到它。`CONFLICT_KINDS` 由事件编解码器持有（工作指派的经验），写入接缝与解码器执法同一收口集合。
- **冲突经一条已记录决议收拢**：`status` 收口为 `OPEN`/`RESOLVED`，两侧皆有写入者；`resolveConflict` 在单个 `BEGIN IMMEDIATE` 内移动开启的行，并要求一条 v1.6b 决策域已为同项目记录的决议（`decisions` 表不带项目列，故校验经 `decision_requests` 联查）。解决的 `resolution_decision_id` 就是冲突的答案——账本记录在案的决策，而非自由文本。已解决的冲突不再二次解决，且每次迁移都携带其必需事件——`conflict/recorded`、`conflict/resolved`——因为没有事件的行迁移是重放无法重建的 fold。
- **事件格式 9，遵守相邻读取契约**：两个事件加入必需词表（29 → 31）；id `cf:<projectId>:<eventSequence>` 由时间线派生。创建与解决时间戳不进重放事实——fold 派生 `status` 并保留解决决议 id，行同决策域的决策文本一样持有时间戳。drift 收集器比对身份族（提出者加两个条目）、kind、描述文本、状态与解决决议；kind 族在两侧都被 CHECK 收口为单值，故其失配分支带一处窄覆盖豁免。
- **`/project conflicts` 渲染生命周期**：最新在前的行携带两个条目的 stable key、提出者的 actor key、描述，以及按 `resolvedAtMs` 的有无分支的 `open` 或 `resolved by <决议 id> at <时间戳>`——与范围预留视图相同的按有无而非回退的模式。

## 验证

- `project-ledger`、`project-ledger-sqlite` 与 `mini-profile` 三包 376 个测试，三包逐文件 100% 覆盖率；账本条目的存储 verifier 跑的正是这条三包命令。
- 迁移覆盖：真实 v8 数据库经 8→9 升级且行完好；注册表连续性测试在九步成立；裸 SQL 测试钉住四条外键（两个条目、提出者、解决决议）与 kind、status 的 CHECK 词表。
- 格式覆盖：高于本构建的时间戳以 `this build reads up to format 9` 拒绝；两个事件的每个字段都有载荷校验（含 kind 词表），fold 拒绝点名未重放条目或 actor 的 recorded 事件、点名未重放冲突或决议的 resolved 事件，以及对已解决冲突的二次解决。
- parity 覆盖：物化侧与重放侧幽灵、提出者/条目、描述、状态、解决决议失配发现在对账与 doctor 双侧逐一钉住顺序；对账测试同时演练行侧决议与重放侧决议，使 drift 消息两个 `?? 'none'` 半边都跑到。
- 门禁：oxlint 0/0；重复率保持两条克隆的既有基线（doctor 与对账的冲突事实行接口错开锚位，使相同片段低于阈值）；每个编辑过的双语对都重录翻译配对。
- Lane：持久运行经存储 verifier 完成 `SB-CONFLICT-RECORD-001`（计划文档本身不变，故运行内的导入幂等，版本 2 仍是活跃版本）；4K 切片保持绿色；首批行落地后重放对账与 doctor 报 0 drift、0 issues。

## 落选方案

- **如范围预留表那样保留 `project_id`**——拒绝：此处没有项目级唯一性谓词，可经 `work_item_a` 派生的列只是负重；适用工作指派/交接的先例。
- **更宽的 `conflict_kind` 集合（计划级、内容、交接冲突）**——拒绝：今天没有写入者观测到它们；集合在真实第二种类出现时经一次 CHECK 迁移扩张，与 `scope_kind` 的 `PATH` 完全一致。
- **自由文本解决而非决议引用**——拒绝：v1.6b 决策域是账本对问题的记录在案的回答；冲突解决正是这样一种回答，指向它使决策的理据、选项与门记录一跳可达。
- **多次解决或 reopen 写入者**——拒绝：冲突只回答一次；重开的冲突是新记录。`resolution_decision_id` 与 `resolved_at_ms` 来回翻转会让 fold 的状态链含混。
- **把阶段 B 进门时被拒绝的第三次预留记成冲突行**——拒绝：本域记录已发生的撞界，而那条在撞界存在前就被预留接缝拒绝；本增量的证据行记录的是作为冲突的包含型擦边，恰如其分。

## 后果

- 阶段 B 完成：v1.6d 计划的活跃版本携带全部五个 DONE 条目（阶段 A 三个、阶段 B 两个），v1.6d 完成报告可作为独立门步骤跟进。
- 持久账本就地折叠九段时间线（97+19+2+14+15+13+22+13+新增，总时长出）；按预留协调的 agent 现在也有了协调失灵时的账本事实——冲突、其描述、以及回答它的决议，作为一条链可重放。
- 范围预留域文档化的限制——重叠按等值判定——现在有了互补物：冲突域记录该限制放过的东西。
