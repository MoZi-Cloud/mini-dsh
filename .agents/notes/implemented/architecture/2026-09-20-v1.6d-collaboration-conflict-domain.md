# Agent Note: The v1.6d Collaboration-Conflict Domain

Status: implemented

English | [中文](2026-09-20-v1.6d-collaboration-conflict-domain.zh.md)

## Problem

Stage B of the v1.6d collaboration scope closes with collaboration conflicts (blueprint §29): one recorded overlap that slipped through the scope reservations — the equal-value uniqueness check judges only the equal path, so two reserved paths can still collide by containment. The domain inherits the now-eight-layer structure: the schema is 8 with eight frozen steps, so the table lands as exactly one appended 8→9 step; the event format is 8 with 29 required events over a 195-event persistent timeline. The blueprint table needs its usual adaptations, and two questions shape the domain: what a conflict's minimum honest content is, and what closes one.

## Decision

- **Schema v9 as one appended migration (8 → 9)**: one `collaboration_conflicts` table — `project_id` dropped (derives through the first work item row, like the assignment and handoff tables; no project-scoped uniqueness predicate exists here), foreign keys to the two work-item rows, the actor row, and the decisions row directly, the blueprint's `description_content_id` indirection inlined as description text, and its nullable `raised_by_actor_id` and work-item columns closed to required. The seam refuses a conflict of an item with itself: a conflict records two work streams that collided, not one stream reported twice.
- **`conflict_kind` closes to `SCOPE_OVERLAP`**: the blueprint leaves the column unvalued; the one overlap this ledger's reservations cannot prevent is two reserved repository paths overlapping by containment, which the equal-value check does not judge. `CONFLICT_KINDS` is owned by the event codec (the work-assignment lesson), so the write seam validates against the same closed set the decoder enforces.
- **A conflict resolves through a recorded decision**: `status` closes to `OPEN`/`RESOLVED`, both writer-owned; `resolveConflict` moves an open row inside one `BEGIN IMMEDIATE` and requires a decision the v1.6b decisions domain has recorded for the same project (the `decisions` table carries no project column, so the check joins through `decision_requests`). The resolution's `resolution_decision_id` is the conflict's answer — the ledger's recorded decision, not free text. A resolved conflict never resolves again, and every transition carries its required event — `conflict/recorded`, `conflict/resolved` — because a row movement without an event is a fold the replay cannot rebuild.
- **Event format 9 under the adjacent-reads contract**: the two events join the required vocabulary (29 → 31); ids `cf:<projectId>:<eventSequence>` timeline-derived. The created and resolved stamps stay out of the replayed facts — the fold derives `status` and keeps the resolution's decision id, and the row owns the timestamps like the decision domain's decision text. The drift collectors compare the identity family (raiser plus both items), the kind, the description text, the status, and the resolution decision; the kind family is CHECK-closed to one value on both sides, so its mismatch branch carries a narrow coverage exception.
- **`/project conflicts` renders the lifecycle**: newest-first rows carry both items' stable keys, the raiser's actor key, the description, and either `open` or `resolved by <decision id> at <stamp>` branched by presence of `resolvedAtMs` — the same presence-not-fallback pattern the reservations view uses.

## Alternatives considered

- **Keeping `project_id` like the scope-reservation table** — rejected: no uniqueness predicate is project-scoped here, so the column derivable through `work_item_a` is weight; the assignment/handoff precedent applies.
- **A wider `conflict_kind` set (plan-level, content, handoff conflicts)** — rejected: no writer observes those today; the set grows through one CHECK migration when a real second kind appears, exactly like `scope_kind`'s `PATH`.
- **Free-text resolution instead of a decision reference** — rejected: the v1.6b decisions domain is the ledger's recorded answer to a question; a conflict resolution is precisely such an answer, and pointing at it keeps the decision's rationale, options, and gate record one hop away.
- **Multiple resolutions or a reopen writer** — rejected: a conflict answers once; a reopened conflict is a new record. `resolution_decision_id` and `resolved_at_ms` flipping back would make the fold's status chain ambiguous.
- **Recording the refused third reservation from the stage-B entry as a conflict row** — rejected: the domain records overlaps that happened, and the reservation seam refused that one before any overlap existed; the evidence row for this increment records the containment near-miss as the conflict it is.

## Consequences

- Stage B is complete: the v1.6d plan's active version carries all five items DONE (three stage-A, two stage-B), and the v1.6d completion report can follow as its own gated step.
- The persistent ledger folds a nine-stamp timeline in place (97+19+2+14+15+13+22+13+new over the grown timeline); agents coordinating by reservation now also have a ledger fact for when coordination fails — the conflict, its account, and the decision that answered it, replayable as one chain.
- The scope-reservation domain's documented limitation — overlap judged at the equal value — now has its complement: the conflict domain records what that limitation lets through.
