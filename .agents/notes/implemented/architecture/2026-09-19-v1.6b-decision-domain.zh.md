# Agent Note：v1.6b Decision 域

Status: implemented

[English](2026-09-19-v1.6b-decision-domain.md) | 中文

## 问题

§33 进入门于 2026-09-19 通过（账本记录 26 个工作项、4K 门槛本身已是完成的账本条目、owner 经既定 go 门确认价值），提案的 v1.6b 范围随之开启：`decision_requests / decisions`、`approvals`、resource 需求与 actor/role 扩展。账本此前完全没有 decision 域：无表、无事件词汇、无写入接缝、无读取表面。三项结构约束塑造了实现。其一，新增必需事件类型必须升 `PROJECT_EVENT_FORMAT_VERSION`，而解码器对任何与当前构建版本不同的行一律拒绝——直接升版会让所有已提交的 format-1 时间线不可读，包括 97 事件的持久账本与两枚钉住的夹具。其二，物理布局在 `PRAGMA user_version` 之后遵循相邻迁移教义：已提交世代绝不重写，钉住的 v1 夹具必须保持 v1。其三，v1.6 蓝图的表规格使用 v1.6a 从未采用的 `content_id` 间接层与 actor-id 引用（文本内联、actor 为字符串），因此本域是适配而非誊抄。

## 决策

- **schema v2 作为一次追加的迁移步骤（1 → 2）**：`decision_requests`（项目作用域 `UNIQUE(project_id, decision_key)`、`blocking_level` 闭集 `BLOCKING`/`ADVISORY`、状态 `OPEN`/`RESOLVED`）、`decision_options`（`UNIQUE(decision_request_id, option_key)`、至多一个 `recommended`、序号取输入顺序）、`decisions`（`UNIQUE(decision_request_id)`——一条决策解除一个请求）。蓝图的 `UNIQUE(plan_version_id, decision_key)` 改为项目作用域，因为 SQLite 可空 `UNIQUE` 列把 NULL 视为互异，且工作项 stable-key 的先例就是项目作用域；`plan_version_id` 保留为可选的同项目校验引用。
- **事件格式 2 配相邻读取**：`decision/requested` 与 `decision/recorded` 进入必需词汇，格式升到 2；解码器改为只拒绝比构建更新的行（`>` 替代 `!==`），因为词汇是累积的，本构建认得任何更旧写入者可能记录的类型。format-1 时间线因此仍可读，这正是升版不杀已提交账本的关键。
- **已提交的 v1 夹具保持冻结并转为升级探针**：`schema.spec` 把 `v1.6a-empty.db` 与 `v1.6a-populated.db` 复制到临时文件后经 shipped 步骤打开，断言版本 2、decision 表在位、28 条 format-1 事件完好——用真实的 v1 数据库走真实的迁移，而非手工戳记的模拟。
- **id 沿用账本既有派生**：`dr:<projectId>:<decisionKey>`（身份派生，同工作项）、`do:<requestId>:<optionKey>`、`dc:<requestId>:<eventSequence>`（时间线派生，同租约与评估）。
- **两个执行层都校验闭环**：写入接缝拒绝项目内重复键、跨项目 plan version、重复选项键、两个 recommended、已解除的请求、请求未携带的选项；重放折叠额外对指向未重放请求的 `decision/recorded`、选择请求从未携带的选项、二次解除同一请求 fail closed。奇偶校验在两处既有扫掠——`readProjectReplay` 与 doctor 的投影检查——比对请求状态与决策（`requestId`、`decidedBy`）。
- **owner 表面暂为只读**：`/project decisions [<project-id>]` 按最新在前列出请求、选项与解除决策；写入保持为库接缝，由 owner 的脚本直接调用（与 supersede/activation 相同姿态，二者同样没有面向 lane 的 writer）。交互式 owner 写入随 approvals 条目到来。
- **§33 进入确认即第一条记录的决策**：lane 完成实现条目后，一次性脚本对 v1.6b plan 版本开出 `v1.6b-entry` 请求（选项：enter（推荐）/ keep accumulating / more evidence），并记录 owner 的 `enter` 决策、引用门槛证据——decision 域的第一次真实使用，就是打开它的那道门的记录。

## 验证

- `project-ledger`、`project-ledger-sqlite`、`mini-profile` 三包 269 项测试、per-file 100% 覆盖；账本条目的存储 verifier 跑的正是这条三包命令。
- 迁移覆盖：先 shipped 0→1 再戳记 1 的数据库经 1→2 升级且行无损；已提交 v1 夹具在副本上就地升级；两步注册表的连续性测试仍然成立。
- 格式覆盖：format-1 行在 format-2 构建下可解码；format-3 行以 `this build reads up to format 2` 拒绝；载荷校验覆盖两个新事件的每个字段，含选项数组结构、blocking-level 成员、折叠内 plan-version 存在性、选中选项成员性。
- 奇偶覆盖：请求与决策的 materialized-only 与 replayed-only 双向漂移、状态与作者不一致，在审计与 doctor 中均有精确断言文本。
- 门：oxlint 0/0、tsc 干净、duplication 维持存量双克隆基线（无新增）、每个编辑过的双语对已重录翻译配对。
- lane：临时首验绿；持久运行导入 v1.6b plan（独立 plan id——post-v1.6a v5 在自己的 plan 下保持 ACTIVE），经存储 verifier 完成 `PB-DECISION-RECORD-001`，幂等重跑零写入通过。

## 考虑过的替代方案

- **在每个读取点各自放宽解码器的精确版本检查** —— 否决：格式常量只有一个家和一个解码器，在那里泛化比较即是全部改动。
- **把夹具重生成到 v2** —— 否决：那会重写已提交世代并抹掉树里仅有的真实 v1 数据库；冻结它们反而换来迁移探针。
- **decision 事件记为 ignorable（不升格式）** —— 否决：decision 物化行，投影语义不得藏进 ignorable 行（§16）。
- **独立的选项注册接缝** —— 否决：选项只作为一个请求开启事务的一部分存在；独立写入者会为没有消费者的事放行半开的请求。
- **§33 确认只记文字** —— 否决：§33 要的是账本证据，域的第一行比日志一行有力得多。

## 后果

- 未来任何必需词汇新增再次升格式并继承相邻读取契约：更旧的戳记可解码，更新的戳记 fail closed。
- 持久账本在新构建首次打开时就地迁移 1→2；其 97 条 format-1 事件如今在 format-2 编解码器下重放（混合戳记时间线的审计保持干净）。
- `PB-APPROVAL-RECORD-001`（按类型化 subject 引用的 approvals，按蓝图一锤定音与 decisions 分表）在 v1.6b 计划中可领取；actor/role 扩展与 resource 域随后。
- `/project decisions` 视图与 decision 表给 owner 一个持久的答案——"我们何时、凭什么证据、决定了什么"——digest 与 export 稍后可以聚合它。
