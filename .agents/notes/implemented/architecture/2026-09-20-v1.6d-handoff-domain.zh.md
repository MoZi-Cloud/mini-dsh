# Agent Note：v1.6d 的交接域

Status: implemented

[English](2026-09-20-v1.6d-handoff-domain.md) | 中文

## 问题

v1.6d 协作范围阶段 A 以交接（蓝图 §28）续篇：一次被记录的工作项在 actor 之间的传递，是双 agent 证据运行得以可能的事件。本域继承如今的六层结构：schema 为 6、六个冻结步骤，所以表恰好以一次追加的 6→7 步骤落地；事件格式为 6、25 个 required 事件，新 required 事件必须升版，又不能作废持久时间线的 97+19+2+14+15+13 混合戳记（160 事件）。蓝图自身的习惯用法需要例行适配，而一列它未赋值之处有真实的前向成本：`handoff_kind` 在蓝图中没有任何枚举，收口错了就意味着扩展 CHECK 还要再付一次迁移。

## 决策

- **Schema v7 为一次追加迁移（6 → 7）**：一张 `handoffs` 表——`work_item_id`、`from_actor_id`、可空的 `to_actor_id`/`to_role_id` 直接引用既有行、`handoff_kind`、内联 `summary`、可空的 `artifact_refs_json`/`memory_refs_json`、`recorded_at_ms`，以及预留的可空 `accepted_at_ms`。没有 `project_id` 列：条目所属项目界定行的作用域，与 `work_leases`、`work_assignments` 相同。item/recorded-time 索引覆盖项目读取路径。
- **恰好一个接收方，处处执法**：接收方 CHECK `(to_actor_id IS NULL) <> (to_role_id IS NULL)`、接缝的 `invalid-argument` 拒绝、负载编解码的 XOR 解码，三者执法同一条规则——交接交给一个 actor 或一个 role，绝不两者皆有，也绝不两者皆无。交接是只追加的记录，所以与指派不同，它不携带在册索引，fold 也不做活跃性扫描。
- **蓝图的内容间接引用折入摘要文本**：`summary_content_id` 变为内联 `summary TEXT NOT NULL`——决策域 `decision_text` 的先例；本没有可指向的内容寻址存储。`repo_snapshot_id` 整体舍弃：v1.6a 账本没有可引用的 repo 快照表。artifact 与 memory 引用以 JSON 对象随接缝序列化进两个可空文本列，负载携带同样的序列化文本（`artifactRefsJson`/`memoryRefsJson`，`constraintsJson` 先例）。
- **`HANDOFF_KINDS` 收口为 `DELEGATE`/`RETURN` 且由事件编解码持有**（`project-events.ts`，`ResourceVerifierKind` 教训）：蓝图让 `handoff_kind` 不赋值，而与 `role_kind`——收口为本账本 role 实际承担的两种职责——不同，目前还没有消费者塑造这个词表。两种已覆盖阶段 A 的故事（一次向前传、一次传回）；只收口这两个是诚实的最小集，扩展的代价反正都是那一步 CHECK 迁移。
- **事件格式 7 在相邻读取契约之下**：`handoff/recorded` 加入 required 词表；id 为 `ho:<projectId>:<eventSequence>`，由时间线派生，因为一个条目会在 actor 之间反复传递。fold 经 `requireReplayedWorkItem`/`requireReplayedActor`/`requireReplayedRole` 解析 item、发送方与接收方，并把摘要与引用文本从重放事实中舍弃——物化行拥有它们，正如 fold 舍弃决策文本。
- **读取经 join 解析标签**：`readProjectHandoffs` 按最新在先返回交接，携带条目的 `stableKey`、两个 actor 的 `actorKey` 与 role 的 `roleName`。预留的 `accepted_at_ms` 在写入者存在之前刻意不进读取形态（分组决策先例）。
- **本域首行指向前方**：`ho:mini-dsh:168` 记录 `PA-CLAIM-VISIBILITY-001` 以 `DELEGATE` 从 lane agent 交给持有 `executor` 角色者，artifact 引用钉住 v1.6d 计划——阶段 A 收拢条目此刻等待的传递，记为事件 168，与 lane 自身的 format-7 戳（161–167）并列。

- 迁移覆盖：真实的 v6 数据库（全部已发布步骤、一行工作指派、戳记 6）经 6→7 升级且行完好；已提交的 v1 fixture 经全部七个已发布步骤升级；注册表连续性测试在七步成立；裸 SQL 测试钉住接收方 CHECK（两个违例方向）、kind CHECK 与四个外键。
- 格式覆盖：比构建更新的戳记以 `this build reads up to format 7` 拒绝；`handoff/recorded` 的每个字段都有负载校验，包括 kind 词表、XOR 接收方规则（两个违例方向）与 fold 的 item/actor/role 存在性检查。

- 门：oxlint 0/0；duplication 回到既有的两条克隆基线（既有的 `project-memory` 配对；本域引入的两个 doctor/replay 孪生窗口已消除——doctor 中 `HandoffFactsRow` 挪位、其接收方检查重构到局部 helper 之后）；每个被编辑的双语对都重录了 translation pairing；文档门全绿。
- Lane：持久运行经存储 verifier 完成 `PA-HANDOFF-RECORD-001`，账本首次打开时就地迁移 6→7；幂等重跑零工具调用通过；4K 切片保持绿色（最大 2,444/4,096）；首行落地后 replay 审计与 doctor 报告 0 drift、0 issues。

## 曾考虑的替代方案

- **更宽的 `handoff_kind` 起点（`DELEGATE`/`RETURN`/`ESCALATE`/`REVIEW`）**——拒绝：没有消费者就发明种类，是死代码的词表版本；两收口已覆盖阶段的故事，CHECK 扩展的代价本来也是一样的。
- **保留 `summary_content_id` 为不透明引用**——拒绝：账本没有内容存储；决策、审批、资源域都已记录内联文本，一个无法解析的 id 会是永久的悬空引用。
- **自由文本 `handoff_kind`（无 CHECK）**——拒绝：蓝图的沉默不是开放字符串列的许可；账本惯例收口种类（`role_kind` 先例），fold 的编解码也需要一个可校验的判别值。
- **镜像指派的状态列（`RECORDED`/`ACCEPTED`）**——拒绝：蓝图把接受记为可空时间戳而非状态；在 `accepted_at_ms` 已预留该状态时再加状态列，是发明没有消费者要的生命周期语义。
- **replay sweep 比对摘要文本**——拒绝：sweep 比对结构事实，决策域的 `decision_text` 已立下内联内容随行与负载走、不做 parity 比对的先例。

## 后果

- v1.6d 阶段 A 批次完成三分之二：`PA-CLAIM-VISIBILITY-001`（按 actor 的领取可见性加双 agent 证据运行）收拢阶段，此刻记录的交接行正是该证据运行要执行的传递。
- 持久账本就地折叠七种戳记的时间线（本增量运行之后为 168 事件中 97+19+2+14+15+13+8）；未来任何 required 词表新增都按同一相邻读取契约再次升版。
- 双 agent 证据运行已能读到自己的原材料：职责行（`wa:mini-dsh:159`/`160`）与交接行（`ho:mini-dsh:168`）点名了可见性改动要投影的 actor 与 role。
