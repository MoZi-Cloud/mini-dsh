# Agent Note: The v1.6b Actor/Role Domain

Status: implemented

English | [中文](2026-09-19-v1.6b-actor-role-domain.zh.md)

## Problem

The v1.6b scope's last family (blueprint §3/§4) makes the people and machines behind the ledger first-class: the decision, approval, and resource domains already record actor strings (`requested_by`, `decided_by`, `raised_by`) and approval `required_role` references, but nothing in the database answers "who is `owner`, what is `executor`". The blueprint's tables carry the same v1.6a-foreign idioms as the three earlier domains — `content_id` indirection on role descriptions, no project-local key on actors (only an optional `external_identity`), lowercase kind/status values — so the layout is again an adaptation. The structural constraints are now four layers deep: the event format is 4 with adjacent reads, three new required events must bump it to 5 without invalidating the persistent timeline's 97+19+2+14 mixed stamps, and the schema is 4 with four frozen steps, so the actor/role layout can only land as exactly one appended 4→5 step. One new design question appears: the blueprint marks `roles.role_kind` `NOT NULL` but specifies no values — closing it to an invented taxonomy risks a wrong guess, dropping a `NOT NULL` column deviates from the blueprint's own table.

## Decision

- **Schema v5 as one appended migration (4 → 5)**: `actors` (project-scoped `UNIQUE(project_id, actor_key)`, kind CHECK `HUMAN`/`AGENT`/`SERVICE`/`SYSTEM`, `INACTIVE` reserved), `roles` (project-scoped `UNIQUE(project_id, role_name)`, kind CHECK `GOVERNANCE`/`EXECUTION`), and `actor_roles` (actor and role references, `valid_from_ms`, reserved nullable `valid_to_ms`). The partial unique index `uq_one_live_assignment_per_pair(actor_id, role_id) WHERE valid_to_ms IS NULL` makes one live assignment per actor-role pair a database fact, not just a seam check; the blueprint's `idx_actors_project_kind` ships unchanged.
- **The actor string is the key** — the adaptation's one added column: `actor_key` follows the `decision_key`/`requirement_key`/`stable_key` pattern and holds exactly the strings the other domains already record, so `actor:mini-dsh:owner` names the same party the approvals table's `decided_by` column does. `external_identity` stays as the blueprint's optional column for a future external directory.
- **`role_kind` closes to the two duties this ledger's roles carry**: `GOVERNANCE` (gating decisions and approvals — the referent `required_role` names, like `owner`) and `EXECUTION` (claiming and completing work, like `executor`). The module doc records that the blueprint leaves the column unvalued and that this build chose the closed set over inventing an open taxonomy.
- **Event format 5 under the same adjacent-reads contract**: `actor/registered`, `role/defined`, and `role/assigned` join the required vocabulary; older stamps decode, newer stamps fail closed. Ids follow the ledger's derivations: `actor:<projectId>:<actorKey>` and `role:<projectId>:<roleName>` by identity, `asg:<projectId>:<eventSequence>` timeline-derived, because ending an assignment (the reserved future writer) must permit re-assignment.
- **Reserved states stay CHECK-legal and writer-less**: `INACTIVE` actors and non-null `valid_to_ms` have no writer yet — the `REVOKED`-lease precedent, recorded in the README's limitations.
- **The fold enforces the same liveness rule the index does**: a `role/assigned` event naming a pair that already holds a live assignment fails replay (`while live assignment "…" already holds it`), mirroring the double-decide and double-resolve rejections; assignments resolve their actor and role through `requireReplayedActor`/`requireReplayedRole`.
- **The shared JSON-object validator became one module**: `json-text.ts` owns `requireJsonObject(field, value, makeError)` — the resource seams had a private copy, and a second private copy in the actors seams would have tripped the duplication gate's token threshold; the callback keeps each domain throwing its own error class while the message text stays identical.
- **Parity covers all three families, both directions**: actors by identity facts (key, kind, display name) and status; roles by identity facts; assignments by pair and validity window — in `readProjectReplay` and the doctor's projection sweep alike.
- **The domain's first rows are the ledger's own cast**: after the lane run, a one-off script registered the two actors the timeline already speaks of (`owner` HUMAN, `agent:mini-real-use-lane` AGENT), defined `owner` (GOVERNANCE — the name the approvals domain's `required_role` already names) and `executor` (EXECUTION), and assigned both — the actor domain's first use is the record of who has been doing the recording.

- Format coverage: a format-6 row rejects with `this build reads up to format 5`; every field of all three events has payload validation, including kind vocabularies, optional string types, and the fold's per-family existence and liveness checks.

The persistent timeline folds formats 1–5 (97+19+2+14+13 stamps over 145 events) clean.

## Alternatives considered

- **Dropping `role_kind` as adaptation noise** — rejected: the blueprint marks it `NOT NULL`, and the governance/execution split is real in this ledger's data (owner gates, the lane executes); a two-value closed set records that fact instead of erasing it.
- **A fourth event ending assignments** — rejected for v1.6b "basic expansion": no consumer exists, and the reserved nullable `valid_to_ms` plus the partial unique index keep the schema honest until one does.
- **Assignment ids by identity (actor + role)** — rejected: re-assignment after a future release writer would collide; timeline-derived ids follow the lease and verification precedent exactly.
- **`role/assigned` payload carrying actor/role keys instead of ids** — rejected: the fold resolves every reference through its projection family (the same fail-closed rule as `decision/recorded` naming `requestId`), so keys would duplicate facts the maps already hold.
- **Leaving `requireJsonObject` duplicated in the actors module** — rejected: an 80-token clone over the duplication gate's threshold; one shared module with an error factory keeps both domains' messages byte-identical.

## Consequences

- The v1.6b plan's version-2 batch is complete: decisions, approvals, resources, and actors/roles all stand as ledger-recorded domains, and the §33 status count reaches 30 items.
- Every actor string the ledger records now has a checkable referent: a typo'd `decided_by` still writes (the columns stay free strings), but `/project actors` names the parties the timeline actually knows.
- Any future required vocabulary addition bumps the format again and inherits the adjacent-read contract; ending assignments or deactivating actors arrives as new seams over the reserved columns, not a migration.
