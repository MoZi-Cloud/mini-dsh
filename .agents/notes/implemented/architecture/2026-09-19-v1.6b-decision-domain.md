# Agent Note: The v1.6b Decision Domain

Status: implemented

English | [中文](2026-09-19-v1.6b-decision-domain.zh.md)

## Problem

The §33 entry gate passed on 2026-09-19 (26 ledger-recorded work items, the 4K bar itself a completed ledger item, and the owner's value confirmation through the established go-gate), which opens the proposal's v1.6b scope: `decision_requests / decisions`, `approvals`, resource requirements, and actor/role expansion. The ledger had no decision domain at all: no tables, no event vocabulary, no write seams, no read surface. Three structural constraints shaped the work. First, adding required event types must bump `PROJECT_EVENT_FORMAT_VERSION`, and the decoder rejected any row whose stamped format differed from the current build — a naive bump would have rendered every committed format-1 timeline unreadable, including the 97-event persistent ledger and both pinned fixtures. Second, the physical layout lives behind `PRAGMA user_version` with the adjacent-migration doctrine: committed generations are never rewritten, so the pinned v1 fixtures had to stay v1. Third, the v1.6 blueprint's table specs use `content_id` indirection and actor-id references that v1.6a never adopted (text inline, actor strings), so the domain is an adaptation, not a transcription.

## Decision

- **Schema v2 as one appended migration step (1 → 2)**: `decision_requests` (project-scoped `UNIQUE(project_id, decision_key)`, `blocking_level` closed set `BLOCKING`/`ADVISORY`, status `OPEN`/`RESOLVED`), `decision_options` (`UNIQUE(decision_request_id, option_key)`, at most one `recommended`, ordinals from input order), and `decisions` (`UNIQUE(decision_request_id)` — one decision resolves one request). The blueprint's `UNIQUE(plan_version_id, decision_key)` became project-scoped because a nullable SQLite `UNIQUE` column treats NULLs as distinct and the work-item stable-key precedent is project-scoped; `plan_version_id` stays an optional same-project validated reference.
- **Event format 2 with adjacent reads**: `decision/requested` and `decision/recorded` joined the required vocabulary, bumping the format to 2; the decoder now rejects only rows stamped newer than the build (`>` instead of `!==`), because the vocabulary is cumulative and this build knows every type an older writer could record. A format-1 timeline is therefore still readable, which is what keeps committed ledgers alive across the bump.
- **The committed v1 fixtures stayed frozen and became upgrade probes**: `schema.spec` copies `v1.6a-empty.db` and `v1.6a-populated.db` to temp files and opens them through the shipped step, asserting version 2, the decision tables present, and the 28 format-1 events intact — a real v1 database exercising the real migration, not a hand-stamped simulation.
- **Ids follow the ledger's existing derivations**: `dr:<projectId>:<decisionKey>` (identity, like work items), `do:<requestId>:<optionKey>`, and `dc:<requestId>:<eventSequence>` (timeline-derived, like leases and evaluations).
- **Both enforcement layers validate the loop**: the write seams reject a duplicate project key, a foreign-project plan version, a repeated option key, two recommended options, a resolved request, and an option the request does not carry; the replay fold additionally fails closed on a `decision/recorded` naming an unreplayed request, selecting an option the request never carried, or resolving one request twice. Parity compares request status and decision (`requestId`, `decidedBy`) in both existing sweeps — `readProjectReplay` and the doctor's projection check.
- **The owner surface is read-only for now**: `/project decisions [<project-id>]` lists requests newest-first with options and resolving decisions; the writes stay library seams the owner's scripts call directly (the same posture as supersede/activation, which have no lane-facing writer either). Interactive owner writers belong with the approvals item.
- **The §33 entry confirmation is the first recorded decision**: after the lane completed the implementation item, a one-off script opened the `v1.6b-entry` request against the v1.6b plan version (options: enter recommended / keep accumulating / more evidence) and recorded the owner's `enter` decision citing the gate evidence — the decision domain's first real use is the record of the gate that opened it.

## Verification

- 269 tests across `project-ledger`, `project-ledger-sqlite`, and `mini-profile` at per-file 100% coverage; the stored verifier for the ledger item runs exactly this three-package invocation.
- Migration coverage: the shipped-0→1-then-stamp-1 database upgrades through 1→2 with rows intact; the committed v1 fixtures upgrade in place on copies; the registry contiguity test still holds with two steps.
- Format coverage: a format-1 row decodes under the format-2 build; a format-3 row rejects with `this build reads up to format 2`; payload validation covers every field of both new events, including option-array structure, blocking-level membership, plan-version existence in the fold, and selected-option membership.
- Parity coverage: materialized-only and replayed-only drift for both requests and decisions, status and author disagreements, in the audit and the doctor, with exact finding texts.
- Gates: oxlint 0/0, tsc clean, duplication at the standing two-clone baseline (no new clones), translation pairing re-recorded for every edited bilingual pair.
- Lanes: temp first-try green; the persistent run imported the v1.6b plan (its own plan id — the post-v1.6a v5 stays ACTIVE under its own plan), completed `PB-DECISION-RECORD-001` through the stored verifier, and the idempotent rerun passed with zero writes.

## Alternatives considered

- **Reaping the decoder's exact-version check per read site** — rejected: the format constant has one home and one decoder; generalizing the comparison there is the whole change.
- **Regenerating the fixtures at v2** — rejected: it would rewrite committed generations and erase the only real v1 databases in tree; freezing them gains the migration probe instead.
- **Ignorable decision events (no format bump)** — rejected: decisions materialize rows, and projection-affecting semantics must not hide in ignorable rows (§16).
- **A separate option-registration seam** — rejected: options exist only as part of one request's opening transaction; a separate writer would admit half-opened requests for no consumer.
- **Recording the §33 confirmation as prose only** — rejected: §33 asks for ledger evidence, and the domain's first row is stronger than a log line.

## Consequences

- Any future required vocabulary addition bumps the format again and inherits the adjacent-read contract: older stamps decode, newer stamps fail closed.
- The persistent ledger migrated 1→2 in place on first open with the new build; its 97 format-1 events now replay under the format-2 codec (the audit stays clean across the mixed-stamp timeline).
- `PB-APPROVAL-RECORD-001` (approvals over typed subject references, kept separate from decisions per the blueprint's ruling) is claimable in the v1.6b plan; actor/role expansion and the resource domain follow.
- The `/project decisions` view and the decision tables give the owner a durable answer to "what did we decide, when, and on what evidence" that the digest and export can later aggregate.
