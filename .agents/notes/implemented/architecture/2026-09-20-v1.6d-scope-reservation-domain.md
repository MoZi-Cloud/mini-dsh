# Agent Note: The v1.6d Scope-Reservation Domain

Status: implemented

English | [中文](2026-09-20-v1.6d-scope-reservation-domain.zh.md)

## Problem

Stage B of the v1.6d collaboration scope opens with scope reservations (blueprint §21): one actor's claim on a project scope while working a work item, so a second agent sees the scope is taken — the stage's parallel-collaboration slice, entered through the §33 gate as decision `dr:mini-dsh:v1.6d-stage-b`. The domain inherits the now-seven-layer structure: the schema is 7 with seven frozen steps, so the table lands as exactly one appended 7→8 step; the event format is 7 with 26 required events over a 195-event persistent timeline. The blueprint table needs its usual adaptations, and one lifecycle question shapes the whole domain: what happens when a reservation's expiry passes and the holder never releases.

## Decision

- **Schema v8 as one appended migration (7 → 8)**: one `scope_reservations` table — `project_id` stays (the blueprint's `idx_scope_active` leads with it, and the scope's uniqueness is project-scoped, unlike the assignment and handoff tables whose `project_id` derived through the item), foreign keys to the work-item and actor rows directly, `scope_kind` closed to the blueprint's unvalued set as `PATH` — the one scope this ledger's agents coordinate on, judged for overlap at the equal value — and `status` closed to `ACTIVE`/`RELEASED`/`EXPIRED`, all three writer-owned. The blueprint's `mode` column is dropped: every reservation ships exclusive, and a column with one legal value is noise, not configurability.
- **One active reservation per project scope is a database fact**: the partial unique index `uq_one_active_reservation_per_scope(project_id, scope_kind, scope_value) WHERE status = 'ACTIVE'`, the seam's `duplicate-reservation` refusal, and the fold's second-active check — all three, the one-live-PRIMARY pattern. The blueprint's `idx_scope_active` ships as-is and an expiry index mirrors the lease reaper's scan.
- **The lifecycle mirrors the work leases, expiry included**: `reserveScope` validates and inserts under one `BEGIN IMMEDIATE`, first expiring a stale row still holding the scope (the claim-path reap: a dead `ACTIVE` row would block the index); `releaseScopeReservation` frees the scope and refuses a second release; `reapExpiredScopeReservations` moves the lapsed batch. Every transition carries its required event — `scope/reserved`, `scope/released`, `scope/expired` — because a row movement without an event is a fold the replay cannot rebuild. `expiresAtMs` is caller-named and must be in the future; no default TTL exists to hide behind.
- **Event format 8 under the adjacent-reads contract**: the three events join the required vocabulary (26 → 29); ids `sr:<projectId>:<eventSequence>` timeline-derived, because a released or expired scope must accept a new reservation. The release and expiry stamps stay out of the replayed facts — the fold derives `status`, and the materialized row owns the timestamps like the decision domain's decision text.
- **`SCOPE_RESERVATION_KINDS` is owned by the event codec** (the work-assignment lesson): the write seam validates against the same closed set the decoder enforces.
- **The read resolves labels through joins**: `readProjectScopeReservations` returns newest-first reservations carrying the item's `stableKey` and the actor's `actorKey`; `/project reservations` renders each row's lifecycle — expiry for `ACTIVE`, the release stamp for `RELEASED`, `expired` for the reaper's rows — branch by presence of `releasedAtMs`, not by an unreachable fallback.

## Alternatives considered

- **Dropping `project_id` like the assignment and handoff tables** — rejected: the scope's uniqueness is project-scoped, so the partial unique index needs the column; the blueprint's `idx_scope_active` leads with it.
- **Keeping the blueprint's `mode` column (`EXCLUSIVE`/`SHARED`)** — rejected: sharing has no consumer, and a one-value CHECK is schema weight without semantics; exclusive is what the table means. The column returns with its CHECK when a second mode exists.
- **Clock-based liveness without an `EXPIRED` writer** — rejected: a stale `ACTIVE` row would block the index forever (no writer to clear it), and moving rows without events would break fold parity; the lease domain's expire-with-event pattern is the proven answer.
- **Closing `scope_kind` to a file/directory/package set** — rejected: no consumer distinguishes them and overlap is judged at the equal value anyway; `PATH` is the honest minimal set, extensible at the cost of one CHECK migration whenever a real second kind appears.
- **A default reservation TTL from config** — rejected: the lease config exists because claim tooling needs a policy default; reservations are library-seam writes whose caller knows the horizon. An implicit TTL would be a hidden `?? default` inside the seam.
