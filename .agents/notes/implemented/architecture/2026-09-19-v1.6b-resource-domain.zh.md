# Agent Note：v1.6b 的 resource 域

Status: implemented

[English](2026-09-19-v1.6b-resource-domain.md) | 中文

## 问题

v1.6b 范围的第三族（蓝图附件 §25/§26/§27）带来资源：项目开启资源需求、实例被提供来满足它们、每个实例对照 spec 被验证。蓝图的三张表带着与 decision、approval 表同样的 v1.6a 陌生习语——带 NULL 陷阱的 `UNIQUE(plan_version_id, requirement_key)`、`content_id` 间接引用、actor id——布局再次是改编。结构约束已叠加到三层深：事件格式为 3 且带相邻读取，三个新的必需事件必须升到 4，却不能让持久时间线的 97+19+2 混合戳失效；schema 为 3、已有三条冻结步骤，resource 布局只能作为恰好一条追加的 3→4 步骤落地。两个新问题出现：`verifier_kind` 放哪里——acceptance 词表拥有同五值的类型，但把 plan 文档类型引进 resource 接缝会重演本树已经领教过的 catalog 重名？以及生命周期走多远——蓝图给了需求和实例状态列，却没有给任何迁移的写入者？

## 决策

- **Schema v4 作为一次追加迁移（3 → 4）**：`resource_requirements`（项目内 `UNIQUE(project_id, requirement_key)`、必填的 JSON 对象形态 `constraints_json`、状态 `OPEN`/`FULFILLED`/`CANCELLED`）、`resource_instances`（需求引用、JSON 对象形态 `metadata_json`、状态 `AVAILABLE`/`RETIRED`）、`resource_verifications`（实例引用、五类 `verifier_kind` CHECK、内联 `verification_spec`、`observed_json`、`PASS`/`FAIL`），各带项目/引用索引。没有一张蓝图表从别的族借来列。
- **保留状态如实呈现**：`FULFILLED`、`CANCELLED` 与 `RETIRED` CHECK 合法但无写入者；`provideResourceInstance` 接缝拒绝非 OPEN 需求，让保留状态在写入者落地前不可达，README 限制区点名它们。这是 `REVOKED` 租约先例。
- **事件格式 4 沿用同一相邻读取契约**：`resource/required`、`resource/provided`、`resource/verified` 进入必需词汇；更旧戳记可解码、更新戳记 fail-closed。id 沿用本库派生式：`rr:<projectId>:<requirementKey>` 按身份，`ri:` 与 `rv:` 与租约、审批一样按时间线派生。
- **verifier kind 词表移入编解码器并改名**：`RESOURCE_VERIFIER_KINDS`（与 acceptance 同五值）由 `project-events` 持有，配资源专属读取器与错误文本，resource 接缝使用 `ResourceVerifierKind`——绝不引用 plan 文档类型。导出同名的公共类型已经让 cordis catalog 静默丢过一条 `dsh-user-approval` 条目；resource 域保留自己的名字，catalog 保持完整、编解码器持有它所校验的词表。
- **JSON 文本字段在解析接缝校验**：`constraintsJson`、`metadataJson`、`observedJson` 存在时必须解析为 JSON 对象；读取接缝存取原文，视图按写入原样展示事实。
- **复验合法，有意为之**：每条 `resource/verified` 事件记录自己的行与时间线派生 id；实例可随事实变化被反复验证，与 acceptance 评估同款。
- **对等覆盖三族、双向**：需求按身份事实（键、类、名）与状态；实例按需求引用与状态；验证按实例引用与结果——`readProjectReplay` 与 doctor 的投影巡检同款。
- **域的第一行是真实资源**：lane 运行后，一次性脚本把持久账本文件本身记为域的第一条需求（`rr:mini-dsh:persistent-ledger`，挂在 v1.6b plan 版本上），文件作为被提供的实例，以刚刚把时间线折叠干净的重放审计作为 PASS 验证——账本关于自身基座的账本证据。
- **计划真实地 supersede 了自己**：导入 `mini-dsh-v16b-owner-decision` 版本 2 经 lane 既有的 supersede-then-activate 路径驱动了 §22 对版本 1 的冻结；版本 2 只列全新稳定键。

## 验证

- `project-ledger`、`project-ledger-sqlite`、`mini-profile` 共 302 项测试、逐文件 100% 覆盖；账本条目的存储 verifier 跑的正是这条三包命令。
- 迁移覆盖：真实 v3 库（全部 shipped 步骤、一条 approval 行、戳 3）经 3→4 升级且行无损；已提交的 v1 夹具在副本上经全部四条步骤升级；注册表连续性测试在四条步骤下成立。
- 格式覆盖：format-5 行以 `this build reads up to format 4` 拒绝；三个事件的每个字段都有载荷校验，含 kind 与 result 词表、可选字符串类型、折叠内逐族存在性。
- 对等覆盖：三族各自的仅物化与仅重放幽灵、身份事实/引用/状态/结果分歧，审计与 doctor 双侧、精确 finding 文本、钉住收集器的推送顺序。
- 门禁：oxlint 0/0、duplication 回到既有两克隆基线（doctor 与 replay 之间一段相同的 import 块以重排一侧打破）、所有编辑过的双语对重新记录 pairing、doc 门 20/20。
- lane：全新 v2 导入的临时首试绿；持久运行 supersede 版本 1、完成 `PB-RESOURCE-RECORD-001`、就地迁移 3→4；重建表面上的幂等重跑零工具调用通过；4K 切片保持绿色（最大 2,444/4,096）。持久时间线跨格式 1–4 折叠 97+19+2+14 个戳（132 事件）干净。

## 考虑过的替代方案

- **复用 `PlanAcceptanceKind` 作为 resource verifier kind**——否决：zod 派生类型会穿过 resource 接缝的 `.run()` 调用（类型安全 lint），且同名导出已经丢过一次 catalog 条目；编解码器持有 `RESOURCE_VERIFIER_KINDS` 让五值相同、名字不同、校验就地。
- **现在就写生命周期迁移**（`FULFILLED`、`CANCELLED`、`RETIRED`）——否决：没有消费者驱动它们，没有调用者的事件是折叠必须永久辩护的词汇条目；CHECK 容纳它们、接缝拒绝它们，写入者随第一个消费者落地。
- **`readProjectResources` 用 join 查询**——否决：三族嵌套两层深，LEFT JOIN 扇出会带着第三层重演 decision 读取的重组；三条有序查询加两个 Map 让嵌套显式、每行单用途。
- **给实例与验证自然键**——否决：蓝图与任何消费者都没给；重复合法（再请求、再验证），两个 id 都像租约与审批一样从事件序列派生。
- **需求/实例/验证分设视图命令**——否决：三族读起来是一个答案（"这个项目需要什么、什么在满足它、它是否成立"）；一个 `/project resources` 视图渲染嵌套，解析步骤保持封闭。

## 后果

- 事件格式与物理 schema 都到了 4；相邻步骤纪律现跨四条步骤，已提交夹具在每次套件运行时全部演练。
- 持久账本把格式 1–4 并排折叠（132 事件中 97+19+2+14）——混合戳时间线如今是常态而非边界情形。
- v1.6b 计划运行在版本 2 上，`PB-ACTOR-ROLE-001`（作为一等行的 actors 与 roles）READY——提案 v1.6b 范围的最后一族；它给 `required_role` 与每个 actor 字符串一个持久指称。
- 资源需求给 owner 证据第三种形态：需求说出项目需要什么，实例说出什么在回应它，验证说出它如何被核验——全部可折叠、可审计、无需 SQL 即可查看。
