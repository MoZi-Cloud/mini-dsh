# Agent Note：v1.6b 的 approval 域

Status: implemented

[English](2026-09-19-v1.6b-approval-domain.md) | 中文

## 问题

v1.6b 计划的第二项（蓝图附件 §24）带来 approvals：owner 的批准挂在类型化主题旁——plan 版本、工作项或决策——由一个 actor 请求、另一个决定，蓝图以一行裁定 declarations 与 approvals 绝不共表。该域继承 decision 域留下的全部约束：事件格式现已为 2 且带相邻读取契约，新增两个必需 approval 事件必须再次升版，却不能让 118 事件的持久时间线失效（97 条戳 1、19 条戳 2）；物理 schema 处于版本 2、只有一条冻结的 1→2 步骤，approvals 表只能作为恰好一条追加的 2→3 步骤落地；蓝图的表规格又用了 v1.6a 从未采用的 `required_role_id` 与 content-id 间接引用，布局依旧是改编而非抄写。一个新问题属于建模：approval 的决定性事实（`decided_by`、decision 文本、`decided_at_ms`）作为整组可选、也作为整组必填——schema 新增的 CHECK 恰好强制这一耦合，读取接缝与 `/project approvals` 视图都必须把它暴露出来，又不能发明合法行永远到不了的回退分支。

## 决策

- **Schema v3 作为一次追加迁移（2 → 3）**：一张 `approvals` 表——`subject_type` 封闭集 `plan-version`/`work-item`/`decision`，`subject_id` 在写入时校验同属一个项目，`required_role`/`requested_by`/`decided_by` 为 actor 字符串，内联 `decision_text`，状态 `PENDING`/`APPROVED`/`REJECTED`——附三条 CHECK 把决定性各列与非 PENDING 状态同进退，并按项目、按 subject 各建索引。decision 各表未加一列；那行裁定在物理布局上成立。
- **事件格式 3 沿用同一相邻读取契约**：`approval/requested` 与 `approval/decided` 进入必需词汇；解码器仍只拒绝比构建更新的戳记，持久时间线上 1/2 混合戳在首批 format-3 行旁保持可读。
- **id 与租约、评估一样由时间线派生**：`ap:<projectId>:<eventSequence>`，在写入者自己的 `BEGIN IMMEDIATE` 内预读分配；approvals 不带自然键，因为蓝图没有给它。
- **决定性事实在读取形状里是一个组**：`readProjectApprovals` 返回 `decision: { decidedBy, decisionText, decidedAtMs } | undefined`，以唯一可空的 `decided_by` 为键、兄弟列经 CHECK 保证转型——与 decision 读取对其 join 的信任同款。视图因此渲染决定行时无需合法行到不了的回退，逐文件覆盖率门也保持诚实。
- **两层都校验闭环**：写入接缝拒绝任一种类的未知或跨项目 subject、非法 outcome、已决定的 approval（`an approval decides exactly once`）；重放折叠另对无对应重放实体的 subject、点名未重放 approval 的 `approval/decided`、对同一 approval 的第二次决定 fail-closed。对等在两条既有巡检——`readProjectReplay` 与 doctor 的投影检查——中双向比较 subject 引用、状态与决定者。
- **§33 进入批准是该域第一行**：lane 完成实现条目后，一次性脚本对 v1.6b plan 版本发起 approval（要求 `owner` 角色、由 owner 请求）并记录 owner 的 APPROVED 决定、援引 §33 门——打开这个域的那道门的批准记录，也是时间线第一批 format-3 行。

## 验证

- `project-ledger`、`project-ledger-sqlite`、`mini-profile` 共 287 项测试、逐文件 100% 覆盖；账本条目的存储 verifier 跑的正是这条三包命令。
- 迁移覆盖：真实 v2 库（两条 shipped 步骤应用、插入一条 decision 行、戳 2）经 2→3 升级且行无损；已提交的 v1 夹具在副本上经两条步骤就地升级；注册表连续性测试在三条步骤下仍成立。
- 格式覆盖：format-1 与 format-2 行在 format-3 构建下解码；format-4 行以 `this build reads up to format 3` 拒绝；两个新事件的每个字段都有载荷校验，含 subject-type 与 outcome 词表、可选字符串类型、折叠内逐种类的 subject 存在性。
- 对等覆盖：双向的仅物化与仅重放 drift、subject/状态/决定者分歧，审计与 doctor 双侧、精确finding 文本——含 CHECK 耦合的篡改形态（已决定行抹回 PENDING 时四列同动；PENDING 行被裸提升时反向同动）。
- 门禁：oxlint 0/0、duplication 维持既有两克隆基线（无新克隆）、所有编辑过的双语对重新记录 pairing、doc 门 20/20。
- lane：临时首试绿；持久运行经存储 verifier 完成 `PB-APPROVAL-RECORD-001`，账本就地迁移 2→3；重建表面上的幂等重跑零工具调用通过；4K 切片保持绿色（最大 2,444/4,096）。

## 考虑过的替代方案

- **对 subject 建多态外键**——否决：SQLite 没有类型联合外键；封闭 subject 词表加写入时逐种类同项目校验、折叠内逐种类存在性校验，以更小表面承载同一保证。
- **读取形状保留三个可选平铺列**——否决：CHECK 使半决定的行不可达，平铺可选列要么逼出不可达的渲染回退、要么留下未覆盖分支；分组的 `decision` 对象把 schema 已强制的耦合写进类型。
- **给 approvals 自然键（项目 + subject + 角色）**——否决：蓝图不给 approvals UNIQUE 约束，同一 subject 被再次请求是合法的（REJECTED 之后再请求）；时间线派生 id 与租约、评估先例一致。
- **第二个事件名用 `approval/recorded`**——否决：该事件记录的是对 approval 的一次决定的结果；`approval/decided` 命名这个动作，接缝对也随之读作 `requestApproval`/`decideApproval`。
- **把 approvals 折进 decisions 表**——否决：蓝图那行裁定（"Decision 与 Approval 不共表"）说得明白，分表也让 decision 域的迁移与对等原封不动。

## 后果

- 事件格式与物理 schema 都到了 3；今后任何必需词汇增补或布局变更再追加一条相邻步骤，并继承"更旧戳记可解码"契约。
- 持久账本现在把 1/2/3 混合戳时间线折叠干净（118 事件中 97/19/2）——本增量 lane 运行写入的七条 format-2 行来自重建前的上一版已构建表面，戳记如实反映其写入者；审计三者皆读。
- v1.6b 计划前两项完成；actors/roles 基础扩展与 resource 域（requirements/instances/verifications，蓝图 §25–27）在后，只读的 `/project approvals` 视图是未来交互式 owner 写入表面要扩展的地方。
- 挂在工作项上的 approvals 给 `work_external_blockers` 的 `APPROVAL` blocker 种类一个可指的持久落点：解除一条 APPROVAL blocker 从此可以意味着被阻塞条目旁有一条已决定的 approval 行。
