# Agent Note：v1.6b 的 actor/role 域

Status: implemented

[English](2026-09-19-v1.6b-actor-role-domain.md) | 中文

## 问题

v1.6b 范围的最后一族（蓝图 §3/§4）让账本背后的人与机器成为一等实体：decision、approval、resource 域已经在记录 actor 字符串（`requested_by`、`decided_by`、`raised_by`）与审批的 `required_role` 引用，但数据库里没有任何东西回答"`owner` 是谁、`executor` 是什么"。蓝图表带着与前三个域同样的 v1.6a 陌生习语——role 描述的 `content_id` 间接引用、actor 没有项目内键（只有可选的 `external_identity`）、小写的 kind/status 值——布局再次是改编。结构约束已叠到四层深：事件格式为 4 且带相邻读取，三个新的必需事件必须升到 5，却不能让持久时间线 97+19+2+14 的混合戳失效；schema 为 4、已有四条冻结步骤，actor/role 布局只能作为恰好一条追加的 4→5 步骤落地。一个新设计问题出现：蓝图把 `roles.role_kind` 标为 `NOT NULL` 却不赋值——收拢成发明的分类法有猜错的风险，删掉 `NOT NULL` 列又偏离蓝图自己的表。

## 决策

- **Schema v5 作为一次追加迁移（4 → 5）**：`actors`（项目内 `UNIQUE(project_id, actor_key)`、kind CHECK `HUMAN`/`AGENT`/`SERVICE`/`SYSTEM`、`INACTIVE` 保留）、`roles`（项目内 `UNIQUE(project_id, role_name)`、kind CHECK `GOVERNANCE`/`EXECUTION`）、`actor_roles`（actor 与 role 引用、`valid_from_ms`、保留的可空 `valid_to_ms`）。部分唯一索引 `uq_one_live_assignment_per_pair(actor_id, role_id) WHERE valid_to_ms IS NULL` 让"每个 actor-role 配对至多一条在册 assignment"成为数据库事实而不只是接缝检查；蓝图的 `idx_actors_project_kind` 原样落地。
- **actor 字符串就是键**——改编中唯一新增的列：`actor_key` 沿用 `decision_key`/`requirement_key`/`stable_key` 模式，持有的正是其他域已在记录的那些字符串，`actor:mini-dsh:owner` 与 approvals 表 `decided_by` 列里的名字指同一方。`external_identity` 作为蓝图的可选列保留给未来的外部名录。
- **`role_kind` 收拢为本账本角色实际承担的两种职责**：`GOVERNANCE`（把关决策与审批——`required_role` 所指的名字，如 `owner`）与 `EXECUTION`（领取并完成工作，如 `executor`）。模块文档记下蓝图未给该列赋值、本构建选择封闭集而非发明开放分类法。
- **事件格式 5 沿用同一相邻读取契约**：`actor/registered`、`role/defined`、`role/assigned` 进入必需词汇；更旧戳记可解码、更新戳记 fail-closed。id 沿用本库派生式：`actor:<projectId>:<actorKey>` 与 `role:<projectId>:<roleName>` 按身份，`asg:<projectId>:<eventSequence>` 按时间线派生——因为终止 assignment（保留中的未来写入者）落地后必须允许重新授予。
- **保留状态保持 CHECK 合法且无写入者**：`INACTIVE` actor 与非空 `valid_to_ms` 暂无写入者——`REVOKED` 租约先例，已记入 README 限制区。
- **折叠强制与索引相同的在册规则**：`role/assigned` 事件若指名已持有一条在册 assignment 的配对，重放失败（`while live assignment "…" already holds it`），与重复决定、重复解除的拒绝同款；assignment 经 `requireReplayedActor`/`requireReplayedRole` 解析其 actor 与 role。
- **共享的 JSON 对象校验器收成一个模块**：`json-text.ts` 持有 `requireJsonObject(field, value, makeError)`——resource 接缝原有一份私有副本，actors 接缝再抄一份就会触到 duplication 门槛的 token 阈值；回调让每个域抛自己的错误类，同时消息文本保持逐字节一致。
- **对等覆盖三族、双向**：actor 按身份事实（键、类、显示名）与状态；role 按身份事实；assignment 按配对与有效期窗口——`readProjectReplay` 与 doctor 的投影巡检同款。
- **域的第一行是账本自己的班底**：lane 运行后，一次性脚本注册时间线早已在谈论的两个 actor（`owner` HUMAN、`agent:mini-real-use-lane` AGENT），定义 `owner`（GOVERNANCE——approvals 域 `required_role` 已指向的名字）与 `executor`（EXECUTION），并双双授予——actor 域的第一次使用，就是记录"一直在做记录的是谁"。

## 验证

- `project-ledger`、`project-ledger-sqlite`、`mini-profile` 共 318 项测试、逐文件 100% 覆盖；账本条目的存储 verifier 跑的正是这条三包命令。
- 迁移覆盖：真实 v4 库（全部 shipped 步骤、一条 resource 行、戳 4）经 4→5 升级且行无损；已提交的 v1 夹具经全部五条 shipped 步骤升级；注册表连续性测试在五条步骤下成立。
- 格式覆盖：format-6 行以 `this build reads up to format 5` 拒绝；三个事件的每个字段都有载荷校验，含 kind 词表、可选字符串类型、折叠内逐族存在性与在册检查。
- 对等覆盖：三族各自的仅物化与仅重放幽灵、身份/状态/配对/有效期分歧，审计与 doctor 双侧、精确 finding 文本、钉住收集器推送顺序。
- 门禁：oxlint 0/0、duplication 回到既有两克隆基线、所有编辑过的双语对重新记录 pairing、doc 门绿色。
- lane：全新 v2 导入的临时首试绿；持久运行完成 `PB-ACTOR-ROLE-001` 并在首次打开时就地迁移 4→5；重建表面上的幂等重跑零工具调用通过；4K 切片保持绿色（最大 2,444/4,096）。持久时间线跨格式 1–5 折叠 97+19+2+14+13 个戳（145 事件）干净。

## 备选方案

- **把 `role_kind` 当改编噪音删掉**——拒绝：蓝图标它 `NOT NULL`，且治理/执行的划分在本账本数据里是真实的（owner 把关、lane 执行）；两值封闭集记录这个事实而不是抹掉它。
- **加第四个终止 assignment 的事件**——v1.6b"基础扩展"拒绝：尚无消费者，保留的可空 `valid_to_ms` 加部分唯一索引让 schema 在消费者到来前保持诚实。
- **assignment id 按身份（actor + role）派生**——拒绝：未来的终止写入者落地后重新授予会撞键；按时间线派生与租约、验证的先例完全一致。
- **`role/assigned` 载荷携带 actor/role 键而非 id**——拒绝：折叠把每个引用经其投影族解析（与 `decision/recorded` 指名 `requestId` 同一 fail-closed 规则），键只会重复映射已持有的事实。
- **让 `requireJsonObject` 在 actors 模块留一份副本**——拒绝：超过 duplication 门槛的 80-token 克隆；一个带错误工厂的共享模块让两个域的消息逐字节一致。

## 后果

- v1.6b 计划的版本 2 批次完成：decisions、approvals、resources 与 actors/roles 全部立为账本记录的域，§33 状态计数达到 30 项。
- 账本记录的每条 actor 字符串现在都有可校验的指涉：打错字的 `decided_by` 仍会写入（各列保持自由字符串），但 `/project actors` 点名时间线真正认识各方。
- 未来任何必需词汇增加照旧升格式并继承相邻读取契约；终止 assignment 与停用 actor 将作为保留列之上的新接缝到来，而不是迁移。
