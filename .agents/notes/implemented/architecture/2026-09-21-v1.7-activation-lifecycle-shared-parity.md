# Agent Note: The v1.7 Activation Lifecycle and Shared Replay Parity

Status: implemented

English | [中文](2026-09-21-v1.7-activation-lifecycle-shared-parity.zh.md)

## Problem

The v1.1 review's F-02: activation has no authoritative writer. The required `plan/version-activated` event has no payload decoder and falls through the fold's default, `ReplayedPlanVersion` carries no lifecycle facts, and neither parity sweep can see direct mutation of `plan_versions.status`, the lifecycle timestamps, or `plans.current_version_id`. The v1.6a BOOT acceptance disclosed the deferral ("the ledger stores commands only" — activation was left to a later work package), but every ACTIVE version to date is a raw owner UPDATE, so the timeline alone cannot answer which version was legally activated. Adjacent: the doctor re-implemented projection parity per entity family (versions not among them) while `readProjectReplay` owns the same comparisons — the duplicated organization is how a required event could register without a decoder or fold.

## Decision

- **`activatePlanVersion` is the activation writer (v1.6a §8)**: one `BEGIN IMMEDIATE` requires a `DRAFT` version with a recorded `plan_imports` row and no other `ACTIVE` version of the plan, then writes `status`, `activated_at_ms`, and the `plans.current_version_id` pointer and appends the strict `plan/version-activated` event (`planId`, `planVersionId`, `activatedAtMs`). Import stays activation-free; a version that never entered through the importer cannot activate.
- **The fold owns the version lifecycle**: `plan/version-activated` decodes and folds (status `ACTIVE`, stamp, pointer); `plan/version-superseded` folds its lifecycle columns and repoints the plan only when the pointer named the retired version, mirroring the writer. The fold does not demand a prior activation for a supersede — the writers gate the transitions, and the persistent timeline holds six supersedes recorded before activation events existed. Activation of an unknown version, of a version whose replayed status is not `DRAFT`, or with a mismatched plan fails closed. Event format 9 → 10; schema stays 9 (`activated_at_ms` and `superseded_at_ms` exist since v1, so no migration is needed and the review's conditional-migration criterion is met by not migrating).
- **Backfill boundary**: an append-only timeline puts any retroactive activation event after the already-recorded supersedes, so a superseded version can never receive a legal-looking activation. The upcoming persistent-ledger backfill covers exactly the currently-ACTIVE versions; the six historical supersedes fold to the shape their events record.
- **Projection parity has one owner**: `readProjectReplay` gains version-lifecycle drift (status, both stamps) and a `currentPlanVersions` pointer comparison in both directions; the doctor's hand-rolled per-family sweep is deleted. The doctor converts replay drift into issues and keeps only lease staleness, the runtime health check replay cannot express. The consolidation lands now because adding lifecycle comparisons a second time would have deepened the duplication the review flagged.
- **Supersede plus activation stays two operations**: the no-ACTIVE interval is documented for callers; the atomicity guarantee attaches to each operation, and no composite switch writer ships without a consumer needing it.

## Verification

- 381 tests across `project-ledger`, `project-ledger-sqlite`, and `mini-profile` cover the new seams: the activation happy path (row, stamp, pointer, event payload, fold, pointer parity), the four activation rejections, activation fold failures (unknown version, foreign plan, malformed fields, non-DRAFT status), supersede folding to pointer-to-successor and pointer-to-none, and lifecycle-tamper findings (status, both stamps, pointer) in the audit.
- Format coverage: a row stamped newer than the build rejects with `this build reads up to format 10`; every fixture that previously activated through raw SQL (six spec files, the mini-profile seeding helpers) now establishes `ACTIVE` through the writer, so parity holds by construction.
- The doctor reports the converted drift findings under its `projection-drift` code and stays silent on clean ledgers; the drift-message wording is pinned through the same collectors `readProjectReplay`'s spec pins.
- Gates: package typecheck green; oxlint clean on the touched packages; translation pairing re-recorded for the edited bilingual pairs.

## Alternatives considered

- **An atomic switch operation (supersede + activate in one transaction)** — rejected for now: no consumer needs the composite, the no-ACTIVE interval is harmless for single-owner flows, and one writer per transition keeps the fold simple. Revisit when a consumer exists.
- **Folding activations only for rows stamped format 10+** — rejected: a fold policy keyed on the row stamp would still replay the six historical versions to `DRAFT` and report drift against their materialized `SUPERSEDED`; the honest model is that the fold reconstructs whatever the events record.
- **Keeping doctor-side version comparisons alongside replay's** — rejected: a second comparison owner is exactly the organization that let `plan/version-activated` register without a decoder or fold; the doctor now owns only what replay cannot express.
- **Backfilling activation events for the six superseded versions** — rejected: the events would land after their supersedes in the append-only timeline and the fold would rightly refuse the sequence; their superseded state is fully reconstructable from the events already recorded.

## Consequences

- The vocabulary documentation no longer lists `plan/version-superseded` as validation-only; a required event type without a decoder and a fold case is now a replay failure, and the standing test that used the activation event as a no-projection-effect specimen is replaced by behavior pins.
- Stage A's remaining items are unblocked: the persistent-ledger backfill (the three currently-ACTIVE versions) and the benchmark workers' migration off direct lifecycle SQL, then F-01's trusted verifier consumer against the same evaluation seam.
- Direct mutation of any version lifecycle column or the plan pointer now surfaces as named drift findings in both `readProjectReplay` and the doctor (A-08), and every ACTIVE version a writer produces traces to its required event (A-06, A-07).
