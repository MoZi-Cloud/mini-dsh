# Agent Note: The v1.6d Handoff Domain

Status: implemented

English | [中文](2026-09-20-v1.6d-handoff-domain.zh.md)

## Problem

Stage A of the v1.6d collaboration scope continues with handoffs (blueprint §28): one recorded pass of a work item between actors, the event that makes the two-agent evidence run possible. The domain inherits the now-six-layer structure: the schema is 6 with six frozen steps, so the table lands as exactly one appended 6→7 step; the event format is 6 with 25 required events, and the new required event must bump it without invalidating the persistent timeline's 97+19+2+14+15+13 mixed stamps (160 events). The blueprint's own idioms need the usual adaptation, and one column it leaves unvalued has real forward cost: `handoff_kind` has no enumeration anywhere in the blueprint, yet closing it wrong means another migration step to extend the CHECK.

## Decision

- **Schema v7 as one appended migration (6 → 7)**: one `handoffs` table — `work_item_id`, `from_actor_id`, nullable `to_actor_id`/`to_role_id` referencing the shipped rows directly, `handoff_kind`, inline `summary`, nullable `artifact_refs_json`/`memory_refs_json`, `recorded_at_ms`, and reserved nullable `accepted_at_ms`. No `project_id` column: the item's project scopes the row, like `work_leases` and `work_assignments`. The item/recorded-time index covers the project read path.
- **Exactly one recipient, everywhere**: the recipient CHECK `(to_actor_id IS NULL) <> (to_role_id IS NULL)`, the seam's `invalid-argument` rejection, and the payload codec's XOR decode all enforce the same rule — a handoff passes to an actor or to a role, never both, never neither. Handoffs are append-only records, so unlike assignments they carry no liveness index or fold scan.
- **The blueprint's content indirection folds into summary text**: `summary_content_id` becomes inline `summary TEXT NOT NULL` — the decision domain's `decision_text` precedent; there is no content-addressed store to point at. `repo_snapshot_id` is dropped outright: the v1.6a ledger has no repo-snapshot table to reference. Artifact and memory references ship as JSON objects the seam serializes into the two nullable text columns, and the payload carries the same serialized text (`artifactRefsJson`/`memoryRefsJson`, the `constraintsJson` precedent).
- **`HANDOFF_KINDS` closes to `DELEGATE`/`RETURN` and is owned by the event codec** (`project-events.ts`, the `ResourceVerifierKind` lesson): the blueprint leaves `handoff_kind` unvalued, and unlike `role_kind` — closed to the two duties the ledger's roles actually carry — no consumer shapes the vocabulary yet. Two kinds cover the stage-A story (a forward pass, a pass back); closing only these is the honest minimal set, and extension costs the CHECK migration step it would cost either way.
- **Event format 7 under the adjacent-reads contract**: `handoff/recorded` joins the required vocabulary; ids `ho:<projectId>:<eventSequence>` timeline-derived, because one item passes between actors repeatedly. The fold resolves item, sender, and recipient through `requireReplayedWorkItem`/`requireReplayedActor`/`requireReplayedRole` and drops the summary and reference texts from the replayed facts — the materialized row owns them, exactly as the fold drops decision text.
- **The read resolves labels through joins**: `readProjectHandoffs` returns newest-first handoffs carrying the item's `stableKey`, both actors' `actorKey` values, and the role's `roleName`. The reserved `accepted_at_ms` is deliberately absent from the read shape until a writer exists (the grouped-decision precedent).
- **The domain's first row points forward**: `ho:mini-dsh:168` records `PA-CLAIM-VISIBILITY-001` handed `DELEGATE` from the lane agent to whoever holds the `executor` role, its artifact refs pinning the v1.6d plan — the pass the stage's closing item waits on, recorded as event 168 beside the lane's own format-7 stamps (161–167).

## Alternatives considered

- **A wider `handoff_kind` start (`DELEGATE`/`RETURN`/`ESCALATE`/`REVIEW`)** — rejected: inventing kinds without a consumer is the vocabulary version of dead code; the two-kinds closure covers the stage's story, and the CHECK extension is the same price it would have been.
- **Keeping `summary_content_id` as an opaque reference** — rejected: the ledger has no content store; the decision, approval, and resource domains already record inline text, and an unresolvable id would be a permanent dangling reference.
- **Free-text `handoff_kind` (no CHECK)** — rejected: the blueprint's silence is not a license for an open string column; the ledger's convention closes kinds (the `role_kind` precedent), and the fold's codec needs a discriminant it can validate.
- **A status column mirroring assignments (`RECORDED`/`ACCEPTED`)** — rejected: the blueprint records acceptance as a nullable timestamp, not a status; adding a status would invent lifecycle semantics no consumer has asked for while `accepted_at_ms` already reserves the state.
- **Comparing summary text in the replay sweep** — rejected: the sweep compares structural facts, and the decision domain's `decision_text` set the precedent that inline content rides in the row and payload without a parity comparison.

## Consequences

- The v1.6d stage-A batch is two-thirds done: `PA-CLAIM-VISIBILITY-001` (per-actor claim visibility plus the two-agent evidence run) closes the stage, and the handoff row recorded now is the pass that evidence run executes against.
- The persistent ledger folds a seven-stamp timeline in place (97+19+2+14+15+13+8 over 168 events after this increment's runs); any future required vocabulary addition bumps the format again under the same adjacent-reads contract.
- The two-agent evidence run can already read its own raw material: the duty rows (`wa:mini-dsh:159`/`160`) and the handoff row (`ho:mini-dsh:168`) name the actors and role the visibility change projects.
